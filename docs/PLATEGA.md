# Platega: интеграция одноразовой оплаты

Проверено 15 сентября 2026 года по [официальному индексу документации](https://docs.platega.io/llms.txt): 31 документ, включая Markdown/OpenAPI и официальный Node.js SDK. Документация читалась через открытый поиск и с сервера. Прямые обращения к Platega с локального компьютера при работе над интеграцией не выполнялись.

## Состояние подключения

Интеграция предназначена для двух независимых экземпляров магазина. До получения API Secret приём платежей Platega должен оставаться выключенным в обоих экземплярах. Наличие Merchant ID само по себе не означает рабочее подключение. Реальные идентификаторы, секреты и адреса магазинов в этот документ не входят.

Серверные настройки:

| Поле | Назначение |
| --- | --- |
| `plategaEnabled` | Разрешение создавать новые платежи; изначально `false` |
| `plategaMerchantId` | Merchant ID из личного кабинета |
| `plategaSecret` | API Secret из личного кабинета |

Секрет хранится только в серверных настройках. Его нельзя помещать в публичные файлы, URL, браузерный JavaScript, журнал запросов или репозиторий. Пустое поле секрета при сохранении настроек сохраняет имеющееся значение; удаление выполняется отдельным действием.

## Выбранная схема

1. Магазин сохраняет заказ и отдельную платёжную попытку до сетевого запроса.
2. Сервер вызывает `POST /v2/transaction/process` без `paymentMethod` и без `id`.
3. Platega возвращает собственный `transactionId` и HTTPS-ссылку `url`.
4. Покупатель выбирает доступный способ на странице Platega. На витрине используется общий способ `ONLINE_PAYMENT` — «Онлайн-оплата».
5. Возврат на страницу магазина открывает проверку состояния. Сам переход по `return` или `failedUrl` не подтверждает и не отменяет оплату.
6. Callback и фоновый опрос запускают одну серверную сверку `GET /transaction/{id}`. Только проверенный результат изменяет финансовое состояние попытки.

Модули: `lib/platega.js` — API, проверка форматов и сопоставление; `lib/platega-callback.js` — обработка уведомления; `server.js` — создание, сверка и опрос; `lib/db.js` — история попыток и переходы состояний.

### Авторизация и проверка подключения

Базовый адрес API — `https://app.platega.io`. Каждый обычный API-запрос использует `X-MerchantId`, `X-Secret` и JSON; секрет отправляется только сервером. Автоматические HTTP-редиректы API запрещены, чтобы заголовки не ушли другому получателю.

Read-only проверка подключения — `GET /balance/all`. Успешный ответ должен соответствовать массиву балансов; выводить сами суммы для проверки не требуется. Пустой массив допустим схемой. Такая проверка подтверждает принятие ключей, но не гарантирует доступность каждого платёжного метода или суммы. `GET` по случайному UUID и ответ `404` не являются надёжной проверкой ключей.

Источники: [авторизация](https://docs.platega.io/), [получение балансов](https://docs.platega.io/получение-балансов-33582950e0).

### Создание платежа

`POST /v2/transaction/process` принимает:

| Поле | Контракт |
| --- | --- |
| `paymentDetails.amount` | Обязательное число в основных денежных единицах; для магазина — рубли |
| `paymentDetails.currency` | Обязательная строка; интеграция использует `RUB` |
| `description` | Обязательная строка описания заказа |
| `return` | Обязательная ссылка возврата покупателя |
| `failedUrl` | Обязательная ссылка возврата при неуспехе |
| `payload` | Необязательная строка; магазин передаёт случайный ID попытки без персональных данных |
| `orderId` | Необязательный внутренний ID платежа; сейчас не используется |
| `metadata` | Необязательный объект; может требоваться для категории магазина |

Если передаётся `metadata`, схема требует строковые `userId` и `userName`. `clientIp` присутствует в примере, но отсутствует в описании свойств. Текущая интеграция не отправляет metadata покупателя. Перед включением нужно уточнить требование для категории магазина; при необходимости добавить стабильный идентификатор плательщика. ID попытки нельзя выдавать за стабильный ID покупателя.

Ответ содержит `transactionId`, `status`, `url`, `expiresIn`, `rate`. Все эти поля обязательны по схеме v2. `expiresIn` задаёт длительность `HH:MM:SS`; значение `00:15:00` — пример, а не обещанный общий срок. Абсолютный срок сохраняется при создании и не продлевается последующими GET.

API генерирует ID транзакции самостоятельно. `orderId` не описан как ключ идемпотентности. Сумма, валюта и payload не входят в обязательный ответ создания v2: финансовую проверку обеспечивает последующий GET.

Источник: [создание без заданного метода](https://docs.platega.io/создание-платежной-ссылки-без-заданного-метода-33845703e0).

### Сверка суммы и статусов

`GET /transaction/{id}` возвращает `id`, `status`, `paymentDetails.amount`, `paymentDetails.currency`, `payload` и дополнительные сведения. В документации поле мерчанта написано `mechantId`. Схема содержит `comission`, `comissionUsdt`, `comissionType`, но не объясняет их влияние на сумму.

Для подтверждения магазин сопоставляет ID транзакции, payload с ID сохранённой попытки, валюту и полную ожидаемую сумму. Денежное сравнение выполняется в целых копейках; третья дробная цифра не округляется до совпадения.

| Platega | Состояние магазина | Действие |
| --- | --- | --- |
| `PENDING` | `pending` | Продолжать проверку |
| `CONFIRMED` | `paid` | Подтвердить только после полного сопоставления |
| `CANCELED` | `cancelled` | Закрыть неоплаченную попытку |
| `CHARGEBACKED` | `refunded` | Зафиксировать возврат после полного сопоставления |
| Неизвестное значение | Без финансового перехода | Сохранить ошибку проверки |

Подтверждение с расхождением суммы/валюты/payload переводит попытку в `mismatch` для разбора. Оно не разрешает выдачу товара. Расхождение при возврате не считается подтверждённым возвратом. Поздний неуспешный ответ не должен отменять ранее подтверждённые деньги; после возврата поздний `CONFIRMED` той же попытки не должен восстанавливать оплату.

**Неопределённость комиссии:** текущие документы и SDK не гарантируют, что комиссия изменяет `paymentDetails.amount` или `callback.amount`, и не задают формулу такого изменения. Поэтому расхождение нельзя автоматически списывать на комиссию, вычитать процент или принимать любую большую сумму. До контрольного платежа и подтверждения правил провайдера применяется строгое равенство.

Источники: [проверка статуса](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0), [PaymentStatus](https://docs.platega.io/paymentstatus-13226215d0), [TransactionStatusResponse](https://docs.platega.io/transactionstatusresponse-13226219d0).

### Callback и два магазина

Адрес обработчика каждого экземпляра: `https://<публичный-домен>/api/pay/platega/callback`. Его указывают в настройках личного кабинета Platega. Требуются публичный HTTPS URL и сертификат доверенного центра; localhost, приватный IP и self-signed сертификат не подходят. Callback не должен требовать браузерную сессию или CSRF-токен.

Уведомление содержит обязательные `id`, `amount`, `currency`, `status`, а также необязательные `paymentMethod`, `payload`. Подлинность проверяется по обоим заголовкам `X-MerchantId` и `X-Secret`. Эти заголовки не являются HMAC-подписью тела. Магазин использует callback как сигнал выполнить GET, а не как самостоятельное доказательство оплаты.

Известная попытка определяется по invoice ID. Payload нужен для дополнительного сопоставления и восстановления привязки после потерянного ответа создания. Неизвестное уведомление аутентифицированного общего мерчанта не меняет заказы этого магазина. Повторное уведомление не должно повторять зачисление, подготовку отправления или уведомление менеджеру.

Platega ожидает `200`; тело ответа не обязательно. При отсутствии успешного ответа в течение 60 секунд предусмотрено до трёх повторов через пять минут. Описание callback включает `CHARGEBACKED`, хотя enum его схемы пока перечисляет только `CONFIRMED` и `CANCELED`; интеграция учитывает описание и общую схему PaymentStatus.

Название раздела ЛК «Callback URLs» **не доказывает поддержку нескольких адресов**. Документация не задаёт число URL, формат списка или правила доставки на несколько сайтов, а per-transaction callback-поля в v2 нет.

- Если ЛК позволяет несколько адресов, зарегистрировать обработчик каждого магазина и проверить фактическую доставку.
- Если доступен один адрес, настроить основной обработчик. Второй магазин подтверждает свои счета независимым фоновым опросом; пересылка callback между магазинами не требуется.
- В обоих случаях каждому магазину нужны собственная история попыток, работающий процесс опроса и доступ к API. Общий мерчант не объединяет базы заказов.
- Попытка без сохранённого invoice ID не опрашивается по GET: восстановление возможно по подходящему callback с payload, иначе нужен ручной поиск в ЛК/выгрузке. Основной callback одного магазина не обеспечивает такое восстановление во втором.

Источник: [callback об изменении статуса](https://docs.platega.io/callback-об-изменении-статуса-транзакции-29209725e0).

### Фоновая проверка и ограничения повторов

Опрос запускается раз в минуту независимо от вкладки покупателя:

| Попытки | Период проверки | Окно автоматической сверки |
| --- | --- | --- |
| `pending` с invoice ID | Не чаще раза в минуту | 7 дней от создания попытки |
| `paid` Platega | Не чаще раза в 15 минут | 30 дней от создания попытки |
| `cancelled`, `expired`, `failed`, `mismatch` с invoice ID | Не чаще раза в 15 минут | 7 дней от создания попытки |
| `refunded` | Повторный опрос не нужен | Состояние сохранено |

Это правила магазина, а не сроки гарантии Platega. За проход обрабатывается до 40 счетов, одновременно до четырёх. Под нагрузкой или при сетевых ошибках фактическая задержка больше указанного интервала. После автоматического окна остаются callback и ручная сверка; для старых возвратов требуется сверка отчётности.

Снятие `plategaEnabled` останавливает новые счета, но сохранённые ключи используются для проверки ранее созданных. Удаление/смена ключей может остановить эту проверку. Один и тот же счёт, одновременно запрошенный callback и polling, проверяется общей задачей процесса.

При неоднозначном результате POST — timeout, сеть, повреждённый или частичный ответ — интеграция не делает автоматический повтор создания. История запроса сохраняется. Повтор того же пользовательского request ID относится к той же попытке; другой запрос временно блокируется установленным защитным интервалом. Этот интервал не означает, что провайдер гарантированно отменил потерянный счёт. При длительной неопределённости нужен разбор в ЛК.

Публичные документы не устанавливают pay-in idempotency, sandbox, тестовые реквизиты, лимиты запросов, min/max одноразового платежа и порядок доставки уведомлений. `Idempotency-Key` из Payout API нельзя переносить в pay-in как гарантию от дублей.

## Включение после получения секрета

1. Сохранить Merchant ID и API Secret в серверных настройках каждого магазина. Сначала оставить `plategaEnabled=false`.
2. Выполнить серверную read-only проверку `GET /balance/all`; убедиться, что ключи принимаются. Не передавать их в поисковые инструменты или диагностические URL.
3. Проверить публичный HTTPS origin каждого магазина и корректность ссылок возврата. Уточнить необходимость `metadata.userId` для категории магазина.
4. Настроить callback по схеме выше. Проверить оба заголовка авторизации, неизвестный invoice, повтор события и временную ошибку GET с последующим повтором.
5. Убедиться, что фоновая сверка работает в обоих экземплярах и журналы не содержат секретов. Для каждого каталога JSON-данных должен работать один процесс записи; локальные блокировки не заменяют межпроцессную координацию.
6. Включить Platega в нужных экземплярах. Провести согласованный контрольный платёж через обычное оформление на каждом сайте: проверить сумму, выбранный метод, возврат, payload, подтверждение, запись в истории и отсутствие дублей.
7. Проверить отменённую оплату и сценарий возврата по фактическому ответу провайдера. Возврат не инициируется автоматически тестом или callback. Проверить поведение при недоступном callback: заказ должен подтвердиться через polling.
8. При ошибках выключить новые платежи, сохранив ключи и историю для сверки. Не удалять попытки, по которым могли прийти деньги.

Пока секрет не предоставлен, нельзя утверждать, что проверены реальные ключи, оплата, доступные методы мерчанта, доставка callback или фактическая сумма после комиссии. Мок-тесты проверяют обработку контрактов и гонок, но не заменяют контрольный платёж.

- [CreateTransactionRequest](https://docs.platega.io/createtransactionrequest-13226217d0): общая схема создания; актуальное описание endpoint дополняет её metadata и orderId.
- [CreateTransactionResponse](https://docs.platega.io/createtransactionresponse-13226218d0): ответ создания с методом; `paymentDetails` допускает строку либо объект. Не подменяет отдельную v2-схему.
- [TransactionStatusResponse](https://docs.platega.io/transactionstatusresponse-13226219d0): поля проверки транзакции.
- [SubscriptionStatus](https://docs.platega.io/subscriptionstatus-16438392d0): состояния подписки.
- [CallbackSubscriptionStatus](https://docs.platega.io/callbacksubscriptionstatus-16438868d0): события активации, отмены и других изменений подписки.
- [SubscriptionInterval](https://docs.platega.io/subscriptioninterval-16441018d0): единицы периода регулярного списания.
- [CallbackPayload](https://docs.platega.io/callbackpayload-13226220d0): общая структура уведомления; проверять вместе с описанием самого callback.

## Старые источники и расхождения

[GitBook](https://platega-io.gitbook.io/platega.io-api-dokumentaciya) и [wiki](https://wiki.platega.io/) относятся к прежним контрактам. В них встречаются клиентский `id`, метод `10`, статусы `EXPIRED`/`FAILED` и база `api.platega.io`. Эти детали нельзя смешивать с текущим v2. Основной источник — `docs.platega.io`, API — `app.platega.io`.

Технические расхождения текущих документов: callback enum отстаёт от описания возвратов; пример JSON-экспорта расходится с prose; часть общих схем отстаёт от endpoint; официальный SDK требует `paymentMethod` в callback строже OpenAPI и сохраняет legacy `10`. Собственный адаптер использует необходимый checkout-контракт, явные проверки и безопасную обработку неизвестных ответов.
