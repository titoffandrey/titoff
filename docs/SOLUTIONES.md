# Solutiones: ссылка СБП на сумму заказа

Касса `lk.solutiones.club` («Solutiones Processing», Next.js-кабинет, API под `/api/v1/`). Подключена 17 сентября 2026. **Документации у сервиса нет** — ни страницы, ни OpenAPI, ни `llms.txt`, ни `robots.txt`; в кабинете, в разделе «API-ключи», описаны только два заголовка. Всё ниже снято с живого API **с боевого сервера через Tor**, ни одного запроса к кассе с рабочего Mac не делалось (см. «Как это проверялось»). Ключи, секреты и адреса магазинов в документ не входят.

## Настройки

| Поле | Назначение |
| --- | --- |
| `solutionesEnabled` | Разрешение выдавать новые счета; изначально `false` |
| `solutionesApiKey` | Public key `pk_…` из раздела «API-ключи» (показан открыто, обычное поле) |
| `solutionesApiSecret` | Secret того же ключа — кабинет показывает его **один раз**, при создании |
| `solutionesWebhookSecret` | `whsec_…` из «Настроек» кабинета; не обязателен — без него уведомления отклоняются (403), оплату подтверждает фоновый опрос |
| `solutionesMaxTotal` | Потолок одного платежа, ₽; по умолчанию 19 000 — см. «Лимит: два разных числа» |

Все три сбрасываются при переносе магазина на другой сервер (`SITE_FIELDS` в `scripts/import-store.js`). Секреты — через `keepOrReplaceSecret`: пустое поле оставляет сохранённое, галочка «Удалить» стирает.

## Контракт API (снят с живого сервиса)

Базовый адрес `https://lk.solutiones.club`, заголовки в каждом запросе — `X-Api-Key: pk_…` и `X-Api-Secret: …`. Без них — `401 {"error":"unauthorized"}`. Редиректы адаптер запрещает (`redirect: 'error'`): ключи не должны уехать на адрес из `Location`.

| Запрос | Ответ |
| --- | --- |
| `GET /api/v1/health` | `{ok, service: "solutiones-processing", time}` — без ключей |
| `GET /api/v1/me` | `{merchant: {id, name, currency, commissionBps}, apiKey: {id, publicKey}}` |
| `POST /api/v1/payment/create` | см. ниже |
| `GET /api/v1/payment/status?id=…` либо `?orderId=…` | объект платежа плюс `paidAt`; нет такого — `404 {"error":"not found"}` |

Несуществующие пути отвечают HTML-страницей 404 Next.js (`text/html`), а не JSON: по этому признаку и искались рабочие адреса. `GET` на `payment/create` даёт 405.

### Создание платежа

Тело — JSON, схема Zod (ошибка валидации приходит `400 {"error": "<JSON массива issues>"}` — по ней и восстановлен список полей: заведомо негодные типы у всех ключей дали ошибки только по известным полям, остальное схема молча отбрасывает):

| Поле | Контракт |
| --- | --- |
| `orderId` | строка, **обязательна**; адаптер передаёт id нашей попытки |
| `amount` | строка или число, **обязательна**, **В РУБЛЯХ** |
| `currency` | строка, необязательна; адаптер передаёт `RUB` |
| `description` | строка, необязательна |
| `successUrl`, `failUrl` | строки, необязательны; адаптер передаёт нашу страницу `/pay/:id` (у ссылки СБП возврата нет — покупатель остаётся на нашей странице, ссылка открывается в новой вкладке) |
| `callbackUrl` | строка, необязательна; адаптер передаёт `https://<домен>/api/pay/solutiones/callback` **без query** |

Ответ 200:

```json
{"id":"cmu4moyqb000lbsutsakpilig","orderId":"probe-1789595052","status":"PENDING","amount":"1000","currency":"RUB","payUrl":"https://qr.nspk.ru/AD10104HJJKN6HP99UF9JTN9943UV80E","expiresAt":null,"createdAt":"2026-09-16T21:44:21.204Z"}
```

Три факта, которые нельзя перепутать:

- **`amount` в ответе — КОПЕЙКИ строкой.** На `"10"` пришло `"1000"`, на `12.34` — `"1234"`. Промах здесь ×100 в деньгах, поэтому `minorOf()` в адаптере читает ответ только как целое число копеек, а `toMinor()` — наш запрос как рубли с двумя знаками; сверка идёт в копейках и без округления.
- **`orderId` идемпотентен.** Повторный POST с тем же `orderId` вернул тот же платёж (тот же `id`, `payUrl`, `createdAt`) — второго счёта не создалось. Отсюда `status?orderId=` как ключ восстановления потерянного ответа (см. ниже).
- **`expiresAt` — `null`.** Срок ссылки касса не задаёт; адаптер требует срок магазина (`R.orderPayUntil`, 30 минут от оформления) и берёт его; непустой срок кассы, если он когда-нибудь появится, только сокращает наш, никогда не продлевает.

`payUrl` — динамическая ссылка СБП НСПК (`qr.nspk.ru/…`): на телефоне открывается в приложении банка (или предлагает выбрать банк), на компьютере показывает QR-код и список банков; сумма зашита в ссылку. Сумму по самой ссылке снаружи не прочитать — страница НСПК отдаёт только JS-приложение, а её `proxyapp/*` — конфиги, не данные платежа.

### Статусы

Живьём виден только `PENDING`; событие вебхука в кабинете названо `payment.paid`. Словарь адаптера (`STATUS` в `lib/solutiones.js`): `PENDING/NEW/CREATED/PROCESSING/WAITING` → `pending`; `PAID/SUCCESS/SUCCEEDED/COMPLETED/CONFIRMED` → `paid`; `EXPIRED` → `expired`; `CANCELED/CANCELLED/VOIDED` → `cancelled`; `FAILED/FAIL/DECLINED/REJECTED/ERROR` → `failed`; `REFUNDED/CHARGEBACK/CHARGEBACKED` → `refunded`. Незнакомое слово — `unknown_status`, финансового перехода нет. **Первый реальный оплаченный счёт покажет настоящее написание** — сверить с этим словарём и при расхождении дописать.

### Сверка

`matchesInvoice` — строгая: тот же `id`, валюта `RUB`, сумма до копейки (в обе стороны: у ссылки нет «тарифа способа», как у общей формы Platega, и другая сумма — чужой платёж), `orderId` равен id попытки, способ `SBP_ONLINE`. Не сошлось при `paid` — `mismatch` на разбор менеджеру, отправление не готовится.

## Комиссия

`/me` отвечает `commissionBps: 2100` — **21 %**. В сумму покупателя она не вмешивается: `amount` в ответе равен нашей сумме, и адаптер сверяет ровно её. Удерживается из выплаты магазину. Никакой «комиссии внутри цены», как у Platega, здесь нет — цены каталога не трогаются.

## Лимит: два разных числа, и верить надо меньшему

Первый контрольный заказ владельца на 55 500 ₽ (17 сентября 2026) получил `400 {"error":"Превышен лимит на сумму платежа: максимум 10000 RUB"}`. Менеджер поднял лимит — `/me` стал отдавать `maxPaymentAmount: "16000000"` (копейки, то есть 160 000 ₽), и на 200 000 касса отвечает тем же 400 уже с «максимум 160000 RUB». Но замер с сервера показал второй, настоящий потолок:

| Сумма, ₽ | Ответ на `POST /payment/create` |
| --- | --- |
| 10 000, 15 000, 17 500, 18 000, 18 500, 19 000 | 200, `PENDING`, `payUrl` есть |
| 19 050, 19 200, 19 500, 19 999, 20 000, 25 000, 30 000, 55 500, 100 000, 160 000 | 200, **`FAILED`, `payUrl: null`** |
| 200 000 и выше | 400 «Превышен лимит … максимум 160000 RUB» |

То есть формальный лимит мерчанта и рабочий потолок выпуска QR — разные вещи, и выше ~19 000 ₽ ссылки не будет при любом заявленном лимите. Отсюда:

- **`solutionesMaxTotal`** — настройка, по умолчанию 19 000; заказ дороже в кассу не идёт, а уходит по своим реквизитам или заявкой (`PAYMENTS.modeFor`), как у Platega с её 20 000. Починят выпуск QR — владелец впишет новое число.
- **Живой `maxPaymentAmount` из `/me` режет потолок сверху** (`acceptsAmount(amount, currency, own, settings)`, `own.maxTotal`): щедрая настройка не пошлёт кассе заказ выше её собственного заявления.
- **Счёт `FAILED` уже в ответе на создание — однозначный отказ** (`ambiguous: false`, код `amount`): платить по нему нечем, и запирать покупателя защитным интервалом незачем. Сам счёт сохраняется в истории попытки.
- Пробные счета `probe-limit*` (полтора десятка, от 10 000 до 160 000) висят в кабинете `PENDING`/`FAILED` — по ним никто не платил.

## Как это встроено в магазин

- Адаптер `lib/solutiones.js` — общий контракт касс (`configured / enabled / supports / acceptsAmount / createInvoice / invoice / matchesInvoice / availableOptions / verifyCallback / callbackView`), пятая строка реестра `PROVIDERS` в `lib/payments.js`.
- **Способ — `SBP_ONLINE`** («СБП», `hosted`, `kind: qr`): тот же id, что у прежних прямых счетов СБП Platega, потому что это тот же способ для покупателя — ссылка СБП на сумму заказа. Он в `DEFAULT_IDS`; у уже настроенных сайтов `payMethods` задан явно, и способ там надо отметить руками. На странице оплаты это кнопка «Перейти к оплате» в новой вкладке; при единственной hosted-кассе оформление уводит на ссылку сразу (`directPayMethod`).
- **Потерянный ответ POST восстанавливается** самим `createInvoice`: таймаут/сеть/5xx → `GET status?orderId=<id попытки>`; нашёлся — это тот же счёт (`recovered: true`), дубля нет. Не нашёлся — исход остаётся двусмысленным (POST мог дойти позже), и действует общий защитный интервал `startPaymentRoute`. Однозначный отказ 4xx счёта не создаёт; строка `error` из его тела читается только ради кода словаря (`amount`, `auth`).
- **Callback** — `POST /api/pay/solutiones/callback` (`lib/solutiones-callback.js`): подпись `X-Webhook-Signature: sha256=<hex>` — HMAC-SHA256 от **сырого** тела (`req.rawBody`) секретом `whsec_…`; префикс `sha256=` необязателен. Попытка узнаётся по `id` (наш `invoiceId`) либо `orderId` (id попытки) из тела — корня или вложенного `data`/`payment`. Верная подпись лишь запускает GET-сверку; чужой платёж (второй сайт того же мерчанта) — 200 без изменений; GET, отставший от события, — 503 «повторите».
- Проверка связи в панели — `GET /api/v1/me`, ничего не создаёт; публичный ключ в ответе обязан совпасть с нашим, 401 читается как «ключи не приняты».
- Фоновый опрос — общий (`reconcileOpenPayments`): `pending` раз в минуту, спустя два часа после срока — раз в 15 минут; `expiresAt` у попытки всегда наш, поэтому брошенный счёт не опрашивается ежеминутно неделю.

## Два сайта, один мерчант

Callback URL в кабинете один. Адаптер передаёт `callbackUrl` в каждом платеже — если касса его чтит, каждому сайту приходят свои уведомления; если нет — второй сайт подтверждает оплату фоновым опросом, как с Platega. Чужое уведомление аутентифицированного мерчанта заказы этого магазина не меняет. Проверить фактическую доставку на оба адреса — первым контрольным платежом на каждом сайте.

## Как это проверялось (17 сентября 2026)

Все запросы — с боевого сервера (`ssh istore2-onion`, Tor), `curl` к `lk.solutiones.club`:

1. `GET /`, `/login`, `/_next/static/chunks/webpack-*.js`, `/api/v1/health` — что это за сервис; перебор `/docs`, `/api/v1/docs`, `/openapi.json`, `/llms.txt` — 404, документации нет.
2. Перебор путей под `/api/v1/` с ключами: JSON отвечают только `/me`, `/payment/create` (405 на GET) и `/payment/status`.
3. `POST /payment/create` с `{}` и с негодными типами у двух десятков ключей — список полей из Zod-ошибок.
4. Два пробных счёта с пометкой `probe` (10 ₽ и 12,34 ₽) — форма ответа, единицы суммы, `expiresAt: null`; повторный POST с тем же `orderId` — идемпотентность. **По ним никто не платил; в кабинете они висят `PENDING`.**
5. `GET status` по `id`, по `orderId` и по несуществующему — 200/200/404.

Не проверено и станет известно только с первого настоящего платежа: написание статуса оплаченного счёта, тело вебхука, чтит ли касса `callbackUrl` из платежа. Лимит суммы проверен — см. «Лимит: два разных числа».
