# Мультимагазин техники Apple

Интернет-магазин на **чистом Node.js без внешних зависимостей**: нет `npm install`, сборки и базы данных. Один процесс обслуживает много доменов (мультитенант): каталог и отзывы общие, а бренд, цены и видимость — свои у каждого магазина.

Интерфейс и весь текст — на русском. Комментарии в коде тоже на русском, продолжай в том же стиле.

## Запуск

```bash
node server.js              # http://localhost:3000
PORT=8080 node server.js    # другой порт

node seed.js                # сбросить каталог/отзывы/заказы к catalog.js
node seed.js --all          # сбросить общие настройки и доступ владельца; пароли сайтов сохраняются
node add-novinki.js         # добавить новинки в живой каталог без потери данных
npm run reviews:demo        # обновить синтетические отзывы, сохранив отзывы покупателей
npm run reviews:demo:remove # удалить все синтетические отзывы
```

Входы: витрина `/`, админка магазина `/admin` (`admin`/`admin`), панель владельца `/owner` (`owner`/`owner`).

Данные лежат в `data/*.json` (создаётся при первом запуске, в git не попадает). Загруженные фото — `data/uploads/`.

## SSH-доступ к рабочему серверу

Подключайся только через локальный SSH-alias `istore2-onion`, который уже настроен в `~/.ssh/config` этого Mac:

```bash
ssh istore2-onion
```

Перед подключением пользователь должен открыть Tor Browser и дождаться соединения. Alias направляет SSH через SOCKS Tor Browser на `127.0.0.1:9150`; если Tor Browser закрыт, соединение обязано завершиться ошибкой без перехода на прямой IP.

Сервер развёрнут заново 9 августа 2026 после потери прежней машины (`istore-onion`, алиас оставлен в конфиге, но не отвечает). Хостинг — servers.guru, Amsterdam, Ubuntu 24.04, 20 ГБ диска, 2 ГБ ОЗУ.

На сервере:

- SSH-пользователь — **`root`** (на прежней машине входили под `titoff` и повышались через sudo);
- приложение работает под `titoff`, проект — `/home/titoff/istore`. **Заходим мы под `root`, поэтому `git pull` и любые скрипты в проекте запускаем через `sudo -u titoff -H bash -lc '…'`**: репозиторий принадлежит `titoff`, и от root git отказывается работать с ним вовсе («detected dubious ownership»). Добавлять `safe.directory` не нужно — под root там и не место;
- PM2-процесс — `istore`;
- **данные — `/var/lib/apple-store`, а не `data/` внутри проекта**: процесс запущен с `STORE_DATA_DIR`. Каталог `istore/data` там тоже есть, но он не используется, и правка в нём на витрину не влияет. Любую команду, которая пишет в хранилище, запускай с этой переменной: `STORE_DATA_DIR=/var/lib/apple-store node scripts/demo-reviews.js --apply`. Резервные копии — `/var/lib/apple-store/backups`;
- Tor onion-служба обслуживается `tor@default`. Через onion проброшен **только SSH** (`HiddenServicePort 22`), витрина в Tor не публикуется;
- **`systemctl is-enabled tor@default` отвечает `enabled-runtime`, и это норма.** У `tor@default.service` нет секции `[Install]` вовсе: постоянно включён `tor.service`, а конкретный экземпляр на каждой загрузке подключает генератор systemd через `/run/systemd/generator/tor.service.wants/`. Пугаться и «чинить» это не нужно;
- витрину отдаёт **Caddy** (`/etc/caddy/Caddyfile`, `reverse_proxy 127.0.0.1:3000`) — сертификат и маршрут есть только у `adcapple.com`, `www` уходит на него редиректом 301. Caddy сам перезаписывает `X-Forwarded-Host`, поэтому подменить магазин заголовком снаружи нельзя. Сжатие в Caddy намеренно не включено: Brotli/gzip приложение делает само;
- **блока для голого IP в Caddyfile быть не должно.** Без совпадения по имени Caddy не отдаёт сайт вовсе: на `https://89.125.187.83/` рукопожатие TLS обрывается, потому что сертификата на адрес нет. Порт 80 при этом всё равно отвечает редиректом 308 на `https://<то же самое>` — это встроенный перенаправитель Caddy, он общий для всех имён, витрину не выдаёт и домен не называет. Отключается только через `auto_https disable_redirects` с ручными блоками редиректа, но тогда легко остаться без обновления сертификата, поэтому оставлено как есть;
- **закрытый доступ по IP не прячет связку «домен → адрес»**: сертификаты Let's Encrypt публикуются в Certificate Transparency, а пассивный DNS хранит A-записи. Это защита от того, кто нашёл адрес и подбирает, что на нём висит, а не от того, кто знает домен;
- `TRUST_PROXY` выставлять не нужно: `trustedProxy()` доверяет соединениям с петли, а Caddy ходит именно оттуда;
- **Node 22 LTS лежит в `/usr/local/bin/node`** (распакован из официального тарбола, дистрибутивного `nodejs` в системе нет вовсе). systemd-юнит `pm2-titoff` берёт node из `PATH`, где `/usr/local/bin` идёт первым. Запускать проверки на сервере нужно тем же `/usr/local/bin/node`;
- **ImageMagick обязателен, и его отсутствие ничем не проявляется** (`apt install imagemagick webp`, ставит `/usr/bin/convert`; `magick` — это IM7, у нас IM6, и `detectBin()` пробует `convert` первым). Без него `lib/images.js` тихо возвращает файл как есть: ошибок нет ни в логах, ни в интерфейсе, просто фото остаются исходниками (после переезда — 5120×2880 по 1,6 МБ вместо 1200×1200 по 76 КБ). **Результат `detectBin()` кэшируется на весь процесс**, поэтому после установки обязателен `pm2 restart istore`, иначе процесс так и будет считать, что бинарника нет. Уже загруженные мимо обработки фото чинит `STORE_DATA_DIR=/var/lib/apple-store /usr/local/bin/node refit-photos.js --apply`;
- **`pm2 update` очищает список процессов** — после него обязателен `pm2 resurrect`, иначе витрина отдаёт 502. Список восстанавливается из `~/.pm2/dump.pm2`, поэтому `pm2 save` после любого изменения обязателен: именно в дампе живёт `STORE_DATA_DIR`;
- файрвол `ufw` включён, и **22-й порт снаружи закрыт**: наружу открыты только 80 и 443. SSH доступен исключительно через onion, который ходит по петле, — её `ufw` пропускает всегда. Пароль для входа по SSH не включался ни разу.

Для одиночной команды используй тот же alias:

```bash
ssh -o BatchMode=yes istore2-onion 'cd /home/titoff/istore && pm2 status --no-color'
```

Свежая onion-служба «раскачивается»: сразу после поднятия первые попытки могут упасть с `SOCKS error 6/240/242` или «timed out during banner exchange». Это нормально, повтори через минуту.

**Правило про прямой IP касается не только SSH.** Витрину тоже нельзя дёргать с этого Mac напрямую — ни `curl`, ни `nc`, ни `ping`, ни `openssl s_client`, ни `dig` по домену магазина. Проверять её можно двумя способами: изнутри сервера (`ssh istore2-onion 'curl -s -o /dev/null -w "%{http_code}" localhost:3000/'`) или через Tor-SOCKS (`curl --socks5-hostname 127.0.0.1:9150 …`). Мимо этого правила уже проходили: аналитика приложения кладёт адрес посетителя в `geoCache` **и отправляет его во внешний геосервис**, так что один обычный `curl` по витрине — это готовая запись во внешнем API.

Никогда не подключайся к серверу магазина по прямому IP и не делай автоматический fallback на обычный SSH. Не используй для этого проект, VPN, серверы или SSH-профили KYNEA. Если `istore2-onion` недоступен, сначала проверь Tor Browser; затем попроси пользователя открыть noVNC у хостера. Onion-адрес, приватный ключ и IP не копируй в репозиторий.

### Если снова придётся поднимать сервер с нуля

В консоли хостера (noVNC или SPICE) **вставка невозможна в принципе**: буфер обмена VNC кладёт текст в буфер X11, а у текстового `tty` его нет — Cmd+V приезжает в гостя как `Esc v`. Поэтому длинные строки туда не набивают, а забирают с сервера: в репозитории лежит `setup-onion.sh`, и в консоли достаточно набрать короткую ссылку через сокращатель. Скрипт ставит tor и ufw, кладёт SSH-ключ, поднимает onion только для 22-го порта и печатает адрес **QR-кодом** (`qrencode -t ANSIUTF8`), чтобы не переписывать 56 символов руками.

## Как устроены характеристики с иконками

Поле `specs` товара — строки `Параметр: значение`. Цель подбора в `lib/spec-icons.js` — поставить рядом со строкой **тот же глиф, который Apple ставит рядом с таким же текстом** в highlights на apple.com/shop. Порядок разбора в `pickIcon()`:

1. **Ключ решает первым** — «Экран» (диагональ 6.1″–6.9″ → `display-6X`, Always-On → `display-always-on`, mini-LED → `display-mini-led`), «Камера/Фронталка» (`pickCamera()` по составу системы), «Чип» (бейдж из `CHIPS`, скобки отбрасываются), «Порты/Разъём» → `port`, «Память/ОЗУ» → `storage`, «Защита» → `water`, «Система» → `os`, «Навигация» → `gps`/`gps-dual`, «Корпус … мм» → `case`/`case-ultra` (49 мм), «Материал» → `shield`, «Датчики» → `sensors`.
2. **Общий список `RULES`** по строке «ключ + значение», сверху вниз, первое совпадение выигрывает.
3. Фолбэк — `sparkles`.

**`sparkles` — не только фолбэк.** У Apple это ещё и собственный глиф «Built for AI» на buy-mac, поэтому правило `готов к ии|built for ai` выбирает его осознанно (у семи Mac в каталоге). По одному лишь имени иконки промах от намеренного выбора не отличить, и старая проверка каталога считала эти строки ошибкой. Поэтому подбор разделён: `choose()` возвращает `null`, когда правило не нашлось, `pickIcon()` подставляет вместо него `FALLBACK`, а **`hasIcon(key, value)` отвечает, было ли настоящее совпадение** — именно её использует проверка ниже. На текущем каталоге промахов нет, и это закреплено тестом.

Результат кэшируется в `memo` — одинаковые строки характеристик встречаются у десятков товаров. Хранится результат `choose()`, то есть `null` тоже кэшируется.

Иконки — 62 файла в `public/spec-icons/`, инлайнятся в HTML и красятся через `currentColor`. Все, кроме одной, — оригинальные глифы Apple (совпадают path-в-path с `apple_svg/`). Своя только `shield.svg` (Ceramic Shield): у Apple она есть лишь растром в таблице сравнения. Отсюда правило `.spec-ico svg[stroke]` в `styles.css` — без него CSS зальёт её сплошняком. У `chip.svg` (бейдж «S10» с buy-watch) убрана надпись — остался чистый контур для чипов без своего бейджа (S11 SiP, H2).

При загрузке глифы минифицируются (`minify()` в `spec-icons.js`): выкидывается прозрачная подложка-квадрат, `xmlns` и `focusable`. Повторный глиф на той же странице вставляется ссылкой `<svg><use href="#g-имя"></svg>` — `specIcon(key, val, seen)`, где `seen` живёт в пределах одного `specHighlights()`.

Чтобы добавить свою: положить SVG в `public/spec-icons/` и дописать строку `[/регулярка/i, 'имя-файла']` в `RULES`.

Вёрстка блока повторяет highlights на apple.com: глиф 35 px слева, строка текста 17px/1.47 справа, без плашек и капслока (`.spec-*` в `styles.css`).

`apple_svg/` (в git не попадает) — скрейп buy-страниц apple.com: только SVG-глифы характеристик плюс `manifest.json` с подписью, страницей и sha1 каждого файла. По нему сверяется, тот ли глиф стоит у строки; растровые иконки таблицы сравнения (PNG) удалены как нерабочие для `currentColor`.

## Наличие по вариантам

У каждого цвета и каждой конфигурации есть свой флаг `inStock`. **Флага нет — вариант в наличии**, поэтому старые данные и `catalog.js` читаются без изменений.

В форме владельца варианты хранятся строками в скрытых `<textarea>`: `Название|#hex|нет` и `Метка|доплата|нет`. Третье поле пишется только для распроданных (`parseStock()` в `server.js` понимает `нет`/`no`/`0`/`out`). Галочку «в наличии» рисует `public/color-editor.js`.

На витрине (`lib/render.js`): `variantInStock()` — доступен ли вариант, `firstAvailable()` — какой выбрать по умолчанию (первый цвет может быть распродан), `sellable()` — можно ли купить товар вообще (нужен хотя бы один доступный цвет **и** одна конфигурация). Распроданные кнопки рисуются с `disabled` и классом `out`, поэтому клики по ним браузер не пропускает и JS не нужен.

Наличие задаётся **по атрибуту, не по сочетанию**: «синий распродан» отключает синий целиком, а не только «синий + 1 ТБ».

`/api/order` перепроверяет наличие варианта заново — корзина живёт в `localStorage` и могла сохраниться до того, как вариант распродали.

**Исчезнувшего или невыбранного обязательного варианта достаточно, чтобы позиция стала недоступной** (`variantMissing()` в `lib/variants.js`). Раньше корзина с «9 ТБ» после удаления конфигурации — либо старая позиция вообще без цвета/памяти — могла оформиться как базовая сборка по базовой цене. Теперь `/api/cart` просит выбрать актуальный вариант заново, а `/api/order` такую позицию не принимает.

### Подпись наличия с мигающей точкой

У товара есть поле `stockLevel` — `in` (по умолчанию) или `few`. На странице товара оно рисует строку над кнопкой покупки: зелёная точка «В наличии» либо оранжевая «Осталось несколько штук» (`stockNote()` в `lib/render.js`). Задаётся в форме владельца селектом «Подпись наличия», рядом с галочкой «Товар в наличии».

- **Это не замена `inStock`.** Галочка выключает товар целиком и даёт «Нет в наличии», а `stockLevel` — только подпись у того, что можно купить. Поэтому `stockNote()` возвращает пустую строку, когда `sellable(p)` ложно: иначе рядом с кнопкой «Нет в наличии» висело бы зелёное «В наличии».
- **Поля нет — считаем `in`**, как у флагов вариантов, поэтому старые данные и `catalog.js` читаются без изменений.
- **`viewFor()` в `lib/tenancy.js` обязан его переносить** — представление собирается по полям поимённо, и без явного переноса значение есть в хранилище, но на витрину не доезжает. Та же грабля, что с `forChoice`.
- `stockLevelValue()` в `lib/db.js` принимает только `few`, всё остальное сводит к `in`, а при `undefined` отдаёт прежнее значение — поэтому частичные обновления (`updateProduct` из маршрута загрузки фото) подпись не затирают.
- **Мигание — чистый CSS и ничего больше.** Анимируются только `opacity` и `transform` (`.stock-dot` в `styles.css`): обе идут в композиторе, не вызывают ни перерисовки, ни пересчёта раскладки. Ни скрипта, ни запроса, ни картинки — на скорость загрузки страницы это не влияет. Ореол вокруг точки сделан отдельным слоем `::after` именно поэтому: анимировать `box-shadow` было бы дешевле по разметке, но дороже по отрисовке. При `prefers-reduced-motion` анимация выключается.
- Цвета — уже проверенные в проекте `#0b7a37` (плашка скидки) и `#bf4800` (отметка «Новинка»), а не `var(--accent)`: акцент у сайтов свой и в 14 px может не читаться.

## Дополнительные характеристики

Поле `options` — группы выбора с buy-страниц apple.com: «Покрытие дисплея. Выберите, какое стекло вам подходит», «Связь», «Подставка», «Блок питания». Формат: `[{name, hint, values:[{label, add, inStock, forStorage}]}]`, где `add` — доплата к цене товара, как у памяти и ремешка. Групп может быть сколько угодно, **выбор в каждой обязателен**, итоговая цена = база + память + ремешок + размер ремешка + сумма выбранных значений.

- Наборы лежат в `catalog.js` (`OPT` и одиночные константы рядом) — 32 товара: iPhone («SIM-карта», см. ниже), Mac (чип и ОЗУ), iPad Pro (стекло + связь), остальные iPad и часы (связь), мониторы (стекло + подставка), MacBook Pro (стекло), MacBook Air (блок питания), iMac (порты и клавиатура), Mac mini (сеть), Vision Pro (вставки ZEISS), AirPods 4 («Версия») и AirTag («Комплект»). У остальных AirPods и HomePod таких групп нет и у Apple.
- **У Mac конфигурация — это чип + ОЗУ + накопитель.** Накопитель живёт в `storages`, а `OPT.chip()` и `OPT.ram()` дают две обязательные группы, как на buy-странице. Состав сверен с apple.com (август 2026): iMac и Mac mini — **M4**, Mac Studio — **M4 Max / M3 Ultra**, на M5 только ноутбуки. Доплаты — долларовые Apple по курсу 90 ₽/$, базовые цены свои.
  - **Метка значения ОЗУ несёт слово «ОЗУ»** («32 ГБ ОЗУ»). В названии заявки значения идут через запятую и без имён групп, поэтому рядом с «512 ГБ» накопителя голое «32 ГБ» было бы не отличить: «MacBook Pro 14" (M5) 4 ТБ, Космический чёрный, M5 Max, 128 ГБ ОЗУ, …».
  - **Строка накопителя у таких товаров называется «Накопитель», а не «Память»** (`variantLabel()` в `lib/render.js`): «Память» и «Оперативная память» в соседних строках читаются как одно и то же. У iPhone и iPad, где выбора ОЗУ нет, осталась «Память».

### `forChoice` — значение зависит от выбора в другой группе

У Apple объём памяти и потолок накопителя **определяет чип**: M5 Pro — это 24/48/64 ГБ и 1–4 ТБ, M5 Max с 32-ядерным GPU — ровно 36 ГБ, 8 ТБ бывает только с Max. Прежней привязки `forStorage` (к конфигурации накопителя) для этого мало, поэтому у значения есть `forChoice` — `{'Чип': ['M5 Max, 40 ядер GPU']}`: «доступно, когда в этой группе выбрано одно из этих значений».

- **Работает и у значений групп, и у самих конфигураций** (`storages`): 8 ТБ у MacBook Pro привязано к чипу так же, как 128 ГБ памяти. Ограничения складываются с `forStorage`.
- **Невыбранная группа ничего не прячет.** Иначе на первом рендере, пока выбор пуст, пропали бы все значения разом.
- Зависимость **двусторонняя**: `syncRows()` в `public/app.js` пересобирает и ряды групп, и ряд конфигураций, а выбор, ставший недоступным, сбрасывает на соседний. Чтобы это не зациклилось, `pickOption`/`pickStorage` принимают флаг `quiet` — «выбор сделан пересборкой, цену и повторную пересборку запустит вызывающий».
- Стартовую сборку считает `defaultChoices()` в `lib/render.js` — в два прохода, потому что группы и конфигурация зависят друг от друга. Открывать страницу с варианта, который скрипт тут же спрячет, нельзя.
- **`viewFor()` в `lib/tenancy.js` обязан переносить `forChoice`.** Представление пересобирает варианты, и без явного переноса привязка есть в хранилище, но на витрину не доезжает — ровно на это я и наступил: ряды не фильтровались, хотя данные были верные.
- Формат в скрытых `<textarea>` — хвост `?Чип=M5 Max, 40 ядер GPU`. Своего поля в редакторе у него нет, но `option-editor.js` и `color-editor.js` **проносят его насквозь** через `dataset.forChoice`: без этого форма стирала бы привязку при каждом сохранении, как когда-то `forColor` у ремешков.
- **Одна пара — ровно одно значение; несколько задаются повтором группы** (`?Чип=M5 Pro, 15 ядер CPU;Чип=M5 Pro, 18 ядер CPU`), а хвостов `?` в строке может быть несколько — они складываются. Списка через запятую внутри пары нет и быть не может: **запятая стоит в самой метке чипа**. Пока значения делились запятой, обычное «открыл карточку Mac и нажал Сохранить» разрезало «M5 Max, 32 ядра GPU» надвое, привязка начинала ссылаться на несуществующие значения — и с витрины пропадала вся оперативная память и старший накопитель, а товар становился непокупаемым. Ровно по той же причине `@`-хвост тоже пишется по одному на метку конфигурации (разбор запятой внутри хвоста сохранён — так формат описан ниже и читаются старые строки). Закреплено тестом «привязка к чипу переживает сохранение формы».
- `sync-options.js` переносит `options` и `storages` **вместе** — порознь привязка указала бы на чип, которого на витрине ещё нет, — и отказывается писать, если `forChoice` ссылается на несуществующее значение. Тест дополнительно требует, чтобы у каждого чипа осталась хотя бы одна память и один накопитель.
- **Товар без групп в `catalog.js` скрипт всё равно берёт — но только ради конфигураций.** Пустой список `options` на витрину не едет никогда: свою «Связь» владелец мог добавить в панели, и перенос пустоты её сотрёт. Без этого правила новая доплата за память у iPhone Air (групп у него нет вовсе) до витрины не доезжала: товар отсеивался в самой первой строке цикла.
- **«SIM-карта» — единственная группа не с buy-страницы Apple.** У Apple версия определяется страной продажи, а в одной витрине серого импорта лежат обе, и разница в цене реальная. `OPT.sim(add)` даёт «Только eSIM» (база) и «eSIM + физическая SIM» (+3000 у e-моделей, +4000 у обычных, +5000 у Pro; у пяти товаров с прайсом поставщика доплата своя — см. «Цены»). Базой стоит **американская версия без лотка**: она на сером рынке дешевле, а `parseOptions()` отбрасывает отрицательную доплату (`add >= 0`), поэтому дешёвый вариант обязан быть первым. Группа есть у всех 13 iPhone, **кроме iPhone Air**: он eSIM-only во всех странах, лотка нет ни у одной версии — выбирать не из чего.
- **Две версии AirPods 4 и две фасовки AirTag — одна карточка, а не две** (`AIRPODS_4_ANC` и `AIRTAG_PACK`): у Apple это тоже один товар с выбором. Базовая цена — младший вариант, доплата выводит на прежнюю цену второй карточки (17 990 ₽ и 11 990 ₽). В живом каталоге слияние делает `node merge-products.js --apply`: он приводит оставшийся товар к `catalog.js`, **переносит на него отзывы покупателей и фотографии** второй карточки и только потом её удаляет. Демо-отзывы не переносятся — их набор пересобирается целиком, поэтому после слияния нужен `scripts/demo-reviews.js --apply`. Скрипт идемпотентен и предупреждает о сайтах, где у удаляемой карточки была своя цена.
- **`forStorage` ограничивает значение частью конфигураций** — у Apple нанотекстурное стекло iPad Pro бывает только на 1 ТБ и 2 ТБ. Это единственная связка «по сочетанию» во всей модели вариантов, и устроена она как `forColor` у ремешков: сервер прячет несовместимое значение прямо в разметке (`V.optionFits()` в `lib/render.js`), а `public/app.js` перебирает ряд заново при смене памяти и сбрасывает выбор на доступный. Пустой список — совместимо со всем.
- Разбор выбранного общий для корзины и заказа — `findOptions`/`optionsAdd`/`optionFits` в `lib/variants.js`. `variantMissing()` считает позицию недоступной, если группа не выбрана, значение не найдено **или названа группа, которой у товара нет**: иначе старая корзина ушла бы в заявку по цене базовой сборки. Наличие и совместимость `/api/order` перепроверяет отдельно, как у ремешка.
- Позиция корзины — `id + память + цвет + ремешок + размер + все выбранные значения` (`itemKey` в `public/app.js`), поэтому iPad с нанотекстурой и без — разные строки. В названии заявки значения дописываются через запятую: «iPad Pro 13" (M5) 2 ТБ, Космический чёрный, Нанотекстурное стекло, Wi-Fi + Cellular».
- В форме владельца группы хранятся строками в скрытом `<textarea name="options">`: `# Группа | подсказка`, ниже `- Значение | доплата | нет | @1 ТБ, 2 ТБ`. Разбирает `parseOptions()` в `server.js`, интерфейс рисует `public/option-editor.js` — там вводится **полная цена** товара с этим значением, доплата считается сама, а «только для конфигураций» — галочки, собранные из живого редактора памяти.
- **Живой каталог на сервере из `catalog.js` сам не обновится** (товары засеиваются только при первом запуске): `node sync-options.js` покажет, что изменится, `--apply` запишет. Товар, у которого метки конфигураций разошлись с `catalog.js`, скрипт пропускает с предупреждением — иначе `forStorage` указал бы в пустоту и значение пропало бы с витрины навсегда.

## Цены: прайс поставщика и перенос на витрину

Базовая цена товара живёт в `catalog.js`, но живой каталог из него **не обновляется** — та же ловушка, что с `options`. Переносит её `node sync-prices.js` (`--apply` пишет): только `price`, `oldPrice` и `hotDealPrice`, всё остальное не трогает.

- **Доплаты едут отдельно.** Память и «SIM-карта» лежат в `storages`/`options`, поэтому после смены прайса нужны оба прогона: `sync-prices.js --apply`, затем `sync-options.js --apply`.
- **`hotDealUntil` не переносится вовсе.** В `catalog.js` это `now + 4 * DAY`, и каждый прогон сдвигал бы конец акции на четыре дня вперёд от сегодняшнего числа. Срок задаёт владелец в панели.
- **Цену по акции скрипт правит только там, где акция включена** (`hotDeal === true`). У выключенной сумма лежит мёртвым грузом, и вписывать её из `catalog.js` значит воскрешать снятую владельцем скидку. А у включённой поправить обязательно: после снижения базовой цены старая «скидка» оказывается дороже товара.
- Пары цен проверяются как в `validateProduct()`: старая цена выше базовой, акционная ниже. Не сходится — товар пропускается с предупреждением, а не пишется криво. **Но акционную цену проверяем только у включённой акции**: на сервере у половины товаров лежит сумма давно завершённой скидки, и строгая проверка держала бы базовую цену намертво — 17 Pro Max не давал снизить себя ниже 84 990 ₽ из-за акции, отключённой ещё в августе. Такую дремлющую сумму скрипт не правит, а перечисляет отдельным списком в конце: включать её в панели без правки нельзя.
- **Сайт с ручной ценой новую базовую не увидит** (`sitePriceOf()` в `lib/tenancy.js`). Скрипт про такие сайты предупреждает отдельно — иначе это выглядит как «отработал, а на витрине старая цена»; править их в `/admin/catalog` нужного магазина.

Цены части каталога поставлены **по прайс-листам поставщика**, а не по рынку РФ, как у остальных:

- **минус 30 %** — пять iPhone: 17 Pro Max, 17 Pro, Air, 17 и 16;
- **минус 25 %** — линейка iPhone 15 (все четыре), Apple Watch Series 11 (алюминий), Series 10, Ultra 3, Ultra 2 и все AirPods. Там прайс дан диапазоном «от–до», и берётся **нижняя граница**: витрина показывает цену «от», а верхняя граница — это уже наценка другого продавца.

Прайс на iPhone 15 расписан по каждому объёму отдельно, поэтому шаги за память у них свои (`ST.ph15`, `ph15plus`, `ph15pro`, `ph15pm`) и не всегда растут: **у 15 Plus 512 ГБ дешевле 256 ГБ**, а у 15 переход со 128 на 256 ГБ дороже, чем потом с 256 на 512. Это не опечатка, а живой остаток склада — цифры из прайса перенесены как есть.

У пяти iPhone из первого прайса цена своя у каждой пары «цвет + объём» и отдельно у версий eSIM и SIM+eSIM, а в нашей модели цвет цену не меняет — поэтому:

- за базу объёма взята **самая дешёвая расцветка**: витрина показывает цену «от»;
- доплата за память — разница между объёмами в том же прайсе;
- доплата за физическую SIM — **средняя по объёмам**: в прайсе она гуляет от 400 до 20 000 ₽ и одним числом не задаётся;
- старая цена и цена по акции сдвинуты пропорционально, чтобы процент скидки на витрине остался прежним.

Отсюда же `ST.ph17pm`, `ST.ph17p`, `ST.ph17air`, `ST.ph17` и `ST.ph16` — свои наборы памяти вместо общих `ST.ph256*`/`ST.ph128`: шаг за память у поставщика заметно меньше типового, и общую сетку эти пять товаров ломали бы для всех остальных iPhone. По той же причине у часов появились `ST.watch42s10` (+750 за 46 мм) и `ST.watch42s11` (+1500) вместо общего `ST.watch42` с его +4000.

**Цены не выровнены по всему каталогу — это ожидаемо.** Прайсы приходят на отдельные модели, и рядом с ними стоят карточки со старыми ценами: Apple Watch SE 3 (27 990 ₽) дороже Series 11 на алюминии (23 250 ₽), Series 11 на титане — 72 990 ₽ при алюминии за 23 250 ₽, iPhone 17e дороже iPhone 17. Пока на эти модели не пришёл свой прайс, так и остаётся; выравнивать их «на глаз» нельзя — цены закупочные.

## Форма товара

`productForm(db, product, opts)` в `lib/owner-views.js` разбита на секции: основное, цена, тексты, варианты, фото. `opts = { errors, draft }` — при ошибке форма возвращается с баннером, подсветкой полей и введёнными значениями (`draft` — тело запроса).

Проверяет `validateProduct()` в `server.js`: без неё пустая форма молча создавала товар «Без названия» с ценой 0. Требуются название, категория и цена > 0; старая цена должна быть выше базовой, а цена по акции — ниже. Дубли цветов и конфигураций схлопываются в `parseColors`/`parseStorages`.

Живой предпросмотр цены и раскрытие блока акции — `public/product-form.js`, повторяет логику `lib/deals.js`.

**Цена сайта в `/admin/catalog` проверяется так же.** Нечисловое значение хранилище отбрасывало и раньше (`setSiteOverrides`), но администратор видел «Цены и видимость сохранены» — при этом товар уходил на базовую цену, а прежняя ручная цена пропадала. Теперь маршрут отвечает 400, возвращает форму с введёнными значениями (`draft`), подсвечивает строку классом `row-error` и не пишет ничего. Достаточно набрать «99 990» с пробелом — так цены и набирают руками.

## Порядок товаров на главной

Витрина показывает карточки **в порядке файла** — `homePage` не сортирует ничего, а `siteProductViews()` только фильтрует, сохраняя порядок. Значит порядок в `products.json` и есть порядок на главной; `createProduct` кладёт новый товар через `unshift`, поэтому новинки появляются сверху.

Меняется он в `/owner/products`: строку можно перетащить за ручку или подвинуть стрелками (`public/product-order.js`), каждое изменение сразу уходит в `POST /owner/products/order`. Порядок общий для всех доменов — каталог общий, поэтому из админки сайта его не правят.

- **`db.reorderProducts(ids)` принимает только точную перестановку** текущего списка — то же правило, что у порядка фотографий. Иначе запрос с урезанным списком стирал бы товары мимо `/delete`, а с чужим id добавлял бы пустую позицию. Любое несоответствие — `null`, файл не трогается.
- **Маршрут регистрируется раньше `app.post('/owner/products/:id')`**: побеждает первый совпавший, и сохранение товара иначе приняло бы запрос порядка за форму. Очерёдность закреплена тестом.
- Не сохранилось — строки возвращаются на прежние места по списку `data-order`, а не перезагрузкой страницы: владелец видит, что именно откатилось. Пока идёт запрос, строки не хватаются повторно (`#product-order.is-busy`), иначе два запроса разъезжаются.
- Перетаскивание — обычный HTML5 drag; на телефоне оно не работает, поэтому стрелки не «дубль ради удобства», а единственный способ там.

### Доливка каталога сохраняет id и место карточки

`add-novinki.js` доливает в живой каталог всё, чего там нет из `NOVELTY_IDS` (не только свежие релизы: прошлые поколения, дописанные в `catalog.js` после первого запуска, попадают на витрину тем же способом). Две вещи, которые он обязан сделать помимо самого создания товара:

- **Сверка «уже есть» идёт по id И по названию.** Одного названия мало: владелец переименовывает карточки в панели («iMac 24" (M4)» → «iMac», «Apple Vision Pro (M5)» → «Apple Vision Pro»), и такой товар перестаёт узнаваться по имени, хотя его id занят. `createProduct` тогда выдаёт случайный id, и на витрину приезжает пустой дубль — без фото, без отзывов, с ценой из `catalog.js`. Ровно так на боевой витрине разом появилось шесть дублей: iMac, Mac mini, Mac Studio, оба iPad Pro и Vision Pro. Закреплено тестом.
- **id берётся из `catalog.js`.** `db.createProduct` принимает `data.id`, если это слаг, он свободен и не занят адресами `/owner/products/new` и `/order`; иначе выдаётся случайный. Со случайным id карточка осталась бы **без единого отзыва**: `scripts/demo-reviews.js` генерирует набор по `catalog.js` и кладёт в отзыв `productId` каталожный. Форма владельца `id` не передаёт вовсе — там он всегда новый. Правило закреплено тестом.
- **Карточка встаёт на своё место.** `createProduct` делает `unshift`, и для новинки это правильно, а прошлое поколение оказалось бы выше свежего. Поэтому после добавления скрипт зовёт `db.reorderProducts()` и ставит товар сразу за ближайшим соседом сверху по `catalog.js`, который на витрине уже есть. Расставленный вручную порядок остальных карточек при этом не меняется.

## Свой отзыв виден автору сразу

Новый отзыв создаётся со статусом `pending` и в общий список не попадает: `db.reviewsForProduct(id, true)` отдаёт только `approved`. Чтобы автор видел свой отзыв опубликованным, `/api/reviews` кладёт его id в **его же подписанную cookie-сессию** (`req.session.myReviews`, последние 30). Маршрут `/product/:id` достаёт по этим id ещё не одобренные отзывы и передаёт их в `productPage` через `opts.ownReviews` — там они подмешиваются в список и в счётчик оценки **только для этого посетителя**.

Никаких пометок «на модерации» на витрине нет — по задумке владельца. В панели отзыв висит в очереди как обычно; после одобрения он приходит из общего списка, а из `ownReviews` уходит (фильтр `status !== 'approved'`), поэтому не задваивается.

Рейтинг в карточках каталога считается глобально (`db.ratingFor`), поэтому там свой неодобренный отзыв не учитывается — только на странице товара.

## Отзывы листаются страницами

У популярных товаров по 300 отзывов, и раньше страница несла их все: одна карточка `iPhone 17 Pro Max` весила **283 КБ, из них 243 КБ — отзывы**. Теперь в HTML попадает одна страница `REVIEWS_PER_PAGE = 8` (`lib/render.js`), и карточка весит 47 КБ.

**Именно страницы, а не «Показать ещё».** Кнопка догрузки была первой версией и мешала: после пяти нажатий, чтобы вернуться к началу отзывов, приходилось скроллить весь накопленный список. Листалка держит высоту блока постоянной.

Сортировка и нарезка живут на сервере в одном месте — `reviewsSlice(list, sort, page)`:

- сортировок три (`REVIEW_SORTS`, там же и подписи кнопок): `new` — по дате, `low` — сначала низкие оценки, `high` — сначала высокие. Внутри одной оценки всегда сначала свежие, иначе «низкая оценка» открывает ленту трёхлетними жалобами, которые к нынешнему сервису отношения не имеют. **По умолчанию `new`** — первый элемент списка; что угодно другое (включая старое `helpful` из сохранённых ссылок) приводится к нему, номер страницы зажимается в `1..pages`, поэтому мусор в адресе безопасен;
- разметку карточки даёт `reviewCard(rv)`, разметку листалки — `reviewsPager(slice, base)`. Обе отдаёт и страница товара, и `GET /api/reviews?productId=&sort=&page=` (поля `html` и `pager`), поэтому ни вёрстка отзыва, ни расчёт номеров не продублированы в `public/app.js`.

`reviewsPageNumbers(page, pages)` оставляет в ряду первую, последнюю, текущую и по два соседа, между разрывами — многоточие: у 38 страниц ряд не длиннее девяти кнопок. Дальние соседи помечены классом `rev-far` и скрыты на узком экране — там остаются стрелки, края и ближайшие номера, ряд помещается в одну строку. Стрелка на краю не исчезает, а гасится (`rev-off`), иначе ряд прыгает на первой и последней странице.

**Номера — настоящие ссылки, а не `<button>`.** Каждая ведёт на `/product/:id?rsort=new&rpage=2#reviews`, кнопки сортировки — на `?rsort=…`; сервер такую страницу честно рендерит (`opts.reviewSort`, `opts.reviewPage` в `productPage`). Без JS это обычная постраничная навигация; с JS обработчик отменяет переход, подменяет список с листалкой, пишет адрес через `history.pushState` и прокручивает к началу блока отзывов. Поэтому «назад» в браузере возвращает к прошлой странице отзывов (`popstate`), а ссылку на конкретную страницу можно отправить другому. При сбое сети переходим по той же ссылке — посетитель получает ту же выдачу обычной страницей. `canonical` у всех страниц один — `/product/:id`, поэтому дубли в индекс не попадают.

Свои неодобренные отзывы (`opts.ownReviews`) выводятся отдельным блоком `.reviews-own` **над** списком и в постраничную выдачу не входят: при сортировке «сначала полезные» автор искал бы свой отзыв где-то на пятой странице.

Разбивка по звёздам и средние по аспектам считаются по **всем** отзывам, а не по показанной порции.

### Списки отзывов в панелях тоже страницами

`/owner/reviews` и `/admin/reviews` раньше выгружали **весь** список. На боевых данных это 7000 отзывов: страница весила 4,5 МБ и держала единственный поток **16 секунд** — всё это время витрина не отвечала ни одному посетителю. Теперь обе панели листают по `ADMIN_PER_PAGE = 50` (`lib/render.js`), страница весит 36 КБ и рендерится за 20 мс.

Срез и навигацию дают общие `adminSlice(list, page)` и `adminPager(slice, href)` — у панелей свои query-параметры, поэтому адрес строит переданная функция `href(n)`. Номера берутся из той же `reviewsPageNumbers()`, что и на витрине.

**Сохранение видимости применяется только к отзывам показанной страницы.** Форма `/admin/reviews` несёт скрытое поле `pageIds`, и сервер меняет флаг лишь у пришедших id. Прежнее правило «скрыто всё, у чего нет галочки» со страницами спрятало бы весь остальной список одним нажатием «Сохранить» — на второй странице полей первой просто нет.

**Одобрение и удаление возвращают на ту же страницу и вкладку** — то же правило, что у заказов ниже. Формы в `/owner/reviews` несут скрытые `page` и `status`, адрес собирает `reviewsBackUrl()` в `server.js` (вкладка «Все» и первая страница в адрес не пишутся). Без этого владелец, разбирающий очередь модерации, после каждого «Одобрить» улетал в начало списка из сотни страниц, а «Удалить» вдобавок сбрасывало вкладку «На модерации» на «Все».

### Списки заказов — тоже страницами

Та же ловушка. Заказы не удаляются сами, поэтому список растёт без предела, а `/owner/orders` и `/admin/orders` выгружали его целиком. Замер на 3000 заявок: **2,8 МБ разметки и ~100 мс занятого потока**; дальше линейно — 20 000 заказов это уже ~19 МБ и секунды простоя витрины. Теперь оба списка идут через те же `adminSlice`/`adminPager`: 53 КБ и 2,3 мс.

Порядок файла сохраняется — `createOrder` кладёт заявку через `unshift`, поэтому свежие остаются на первой странице и сортировать ничего не нужно.

**Действие над строкой возвращает на ту же страницу.** Формы смены статуса и удаления несут скрытое `page`, а маршруты собирают адрес через `pageQuery()` в `server.js` (первая страница — адрес без параметра, чтобы ссылки не обрастали мусором). Без этого владелец после каждой правки на седьмой странице оказывался в начале списка.

### Индекс отзывов по товарам

`db.reviewsForProduct()` больше не фильтрует и не сортирует весь массив на каждый вызов. `reviewIndex()` в `lib/db.js` один раз раскладывает отзывы по товарам (`{all, approved, sum}`, оба списка сразу отсортированы от свежих) и кэширует результат. Ключ актуальности — **ссылка на массив**: `readJson` отдаёт один и тот же объект, пока не изменился mtime файла, поэтому `_reviewIndex.src === list` и есть проверка свежести.

Отсюда же берётся рейтинг: `ratingFor()` читает готовые `sum`/`count`, а каталог получает все оценки одним вызовом `db.approvedTotals()`. Сайт, скрывший часть отзывов, **вычитает** их из готовой суммы (`siteTotals()` в `tenancy.js`), а не пересчитывает всё заново — скрытых единицы.

Массивы отдаются **по ссылке**, как и `getReviews()`: мутировать их на месте нельзя. Все вызывающие сначала делают `filter`/`slice`/`concat`, а `sortReviews()` начинает с `list.slice()`.

Итог на боевых данных: главная 6,3 → 2,8 мс, страница товара 9,0 → 4,2 мс.

### Оценка в представлении товара считается лениво

`viewFor()` в `tenancy.js` раньше считал `_rating` сразу. Но `/api/cart` и `/api/order` строят до **100** представлений на один запрос и рейтинг не показывают вовсе — на каждое впустую пробегался список отзывов товара (до 300 записей). Теперь `_rating` — неперечислимый геттер, который при первом чтении подменяет себя готовым значением; вызывающие (`productPage`, `productCard`) ничего не заметили. `siteProductViews()` для каталога по-прежнему передаёт готовые суммы из `approvedTotals()` явным аргументом, поэтому геттер там даже не создаётся.

Свои неодобренные отзывы на `/product/:id` ищутся тоже через индекс (`db.reviewsForProduct(id, false)`), а не перебором всего файла: 300 записей вместо 7000 на каждое открытие страницы любым, кто когда-то оставил отзыв.

### Посетители метрики — по индексу

`findVisitor()` звали на каждый просмотр страницы, каждый heartbeat и каждую заявку, а он перебирал массив; при потолке `MAX_VISITORS = 10 000` это ~0,04 мс на пустом месте в каждом запросе. Теперь рядом живёт `Map` `byId`. **Любая замена массива `visitors` целиком обязана звать `reindex()`** — это `expirePending()`, `cleanup()` и загрузка; точечные `push`/`delete` правят и массив, и карту.

`cleanup()` (срок хранения 365 дней + сортировка до 10 000 карточек) больше не выполняется на каждой записи файла: `flush()` зовёт его не чаще раза в `CLEANUP_MS = 10 минут`, а в остальные разы делает только `expirePending()`. Раньше полная уборка шла дважды в минуту и на каждом заказе.

Замер на 10 000 карточек: 1000 heartbeat 37,6 → 1,1 мс, 1000 просмотров 39,5 → 11,5 мс.

## Даты отзывов не устаревают

Даты считаются от релиза товара до «сегодня» (`reviewDate()`), поэтому набор, сгенерированный один раз, через месяц показывает самый свежий отзыв месячной давности — витрина выглядит заброшенной.

Лечится повторным прогоном, и это дёшево именно потому, что **от текущей даты зависят только `createdAt`**. Тексты, авторы и оценки берутся из ГПСЧ с сидом «id товара:номер», то есть не зависят от времени: при сдвиге «сегодня» на 30 дней автор и оценка совпадают у 100 % отзывов, текст — у 98,9 % (расходятся те, у кого разброс дат поменял соседей местами, а тексты выдаются в порядке показа). Так что повторный прогон не переписывает ленту заново, а сдвигает её вперёд.

На сервере это делает cron пользователя `titoff` — ежедневно в 01:20 UTC (04:20 МСК):

```
20 1 * * * { date -Is; STORE_DATA_DIR=/var/lib/apple-store NODE_BIN=/usr/local/bin/node /home/titoff/istore/scripts/refresh-demo-reviews.sh; } >> /home/titoff/demo-reviews.log 2>&1
```

`scripts/refresh-demo-reviews.sh` (он лежит в репозитории, а не в домашней папке) кладёт откатную копию в `/var/lib/apple-store/backups/reviews-before-refresh.json` и запускает `scripts/demo-reviews.js --apply` с нужным `STORE_DATA_DIR`. Полный прогон занимает 3 с и 72 МБ. Перезапуск процесса не нужен: `readJson` сверяет mtime и подхватывает файл сам.

После обновления самый свежий отзыв товара — сегодняшний, а первая страница из восьми укладывается примерно в неделю.

**Новый товар без записей в `REVIEW_COUNTS` и `RELEASE_DATES` роняет скрипт** (это защита: иначе набор молча потеряет товар). Данные при этом целы — исключение бросается до записи, — но обновление дат встанет, поэтому после `add-novinki.js` загляни в `~/demo-reviews.log`.

## Демо-отзывы не выглядят демо-отзывами

`lib/demo-reviews.js` собирает набор детерминированно (свой ГПСЧ от строки `id товара:номер`), поэтому `npm run reviews:demo` даёт тот же результат и сохраняет добавленные владельцем фото.

**На витрине они неотличимы от настоящих.** Пометки `(демо)` в имени автора больше нет — демо-отзыв опознаётся только по служебным полям (`demo`, `source`, префикс `demo-` в id), по ним же работает `reviews:demo:remove`.

Что делает набор похожим на живую ленту:

- **Цена — главный довод.** `PRICE_POINTS` попадает в `PRICE_SHARE` (60 %) развёрнутых отзывов, итого про цену пишут примерно в 44 % ленты: «тут реально оптовые цены», «дешевле чем у официалов», «мониторил цены месяц». Конкретные сети и маркетплейсы **не называем** — сравнение идёт с «другими магазинами», иначе демо-набор превращается в рекламу против чужого бренда. Это закреплено тестом.
- **Короткие отзывы.** `SHORT_SHARE` (22 %) — одна строка вместо трёх фраз, и внутри них `ULTRA_SHARE` (42 %) — совсем короткие «Все четко», «Получил», «Топ». В сумме каждый девятый отзыв короче 20 символов. Такие тексты **повторяются**, и это правильно: у настоящих покупателей «Все супер» тоже не уникально. Тест требует уникальности только от развёрнутых отзывов (длиннее 60 символов).
- **Ошибки.** Словарные (`TYPO_WORDS`: «вообщем», «нравиться», «бысто») выбираются **только из тех пар, что реально есть в тексте** — иначе замена проходит вхолостую и ошибок в ленте меньше процента. Плюс механическая опечатка `typoInWord()`: пропуск, дубль или перестановка букв. Последнюю букву слова она не трогает — иначе «заказала» превратится в мужскую форму и сломает согласование по полу.
- **Эмодзи и скобки** (`addTail()`): у пятёрок чаще, у троек — только грустный смайлик. В отзыве короче 20 символов вероятность выше на 0.2: там эмодзи заменяет всё, что человек не дописал. Скобка ставится вместо точки, а не после неё.
- **Разговорные названия техники.** Каталожное «iPhone 17 Pro Max» пишут единицы, поэтому `CASUAL_NAMES` держит по нескольку живых вариантов на товар («айфон», «айфон 17 про макс», «ультра», «эйртег», «хоумпод мини»), и `productTitle()` подставляет их в `CASUAL_SHARE` (72 %) случаев. В таблице они лежат **в именительном падеже**, а во фразы вида «брал X» подставляются через `accusative()`: у слов на -а/-я меняется окончание («колонка» → «колонку»), остальные совпадают. Поэтому в таблицу нельзя класть вариант, у которого падежное слово не последнее («колонка эпл» сломается, «эпл колонка» — нет). Незнакомый id (новинка из `add-novinki.js`) уходит на фолбэк `productNoun()` — общее слово вроде «телефон».
- **Разговорный слой.** `CASUAL_TWEAKS` заменяет в готовой фразе «нормально» → «норм», «примерно» → «где-то», «магазин» → «магаз», «ноутбук» → «ноут». Замена идёт по собранному тексту, а не двумя вариантами каждой фразы в пулах, и **до** опечаток — чтобы их так же трепало. Сокращать можно только там, где усечённая основа сохраняет окончание: «магазином» → «магазом» читается, а «телефоном» → «телом» уже нет, поэтому такой пары в таблице нет.
- **Согласование по полу.** `GENDER_FORMS` пишется строчными в одном экземпляре, а варианты с заглавной буквы и готовые регулярки собираются в `ALIGN_RULES` сами. Раньше пары перечислялись вручную в обоих регистрах, форму из начала фразы легко было забыть — и женщина писала «Доволен».
- **Имена.** По умолчанию русские; `REGIONAL_SHARE` (12 %) — имена, распространённые у других народов России. Подпись — одно слово: инициалов и фамилий нет, а в `SHORT_NAME_SHARE` (68 %) случаев стоит короткая форма из `SHORT_NAMES` («Саша», «Серёга», «Настя»). Имена без общепринятого сокращения в этой таблице просто отсутствуют. Новые гендерные формы из коротких текстов обязательно добавляй в пары `alignPhrase()`, иначе женщина напишет «ждал». Регулярки там без `\b` — он не работает с кириллицей.
- **Подписываются не только именем и не только кириллицей.** `LATIN_SHARE` (11 %) — то же имя латиницей по таблице `LATIN_NAMES`: она ручная, потому что люди пишут «Dmitry», а не транслитерацию по правилам. Латиница применяется **после** выбора короткой формы, поэтому «Саша» даёт «Sasha», а не «Alexandr». `NICKNAME_SHARE` (8 %) — ник вместо имени (`kotofey`, `Батя`, `sveta13`, `Покупатель`). Ники с явным полом лежат в `NICK_MALE`/`NICK_FEMALE` и достаются только своей персоне, нейтральные — любой. Подпись по-прежнему одно слово без точек и пробелов.
- **Одна фраза не повторяется в пределах страницы отзывов.** Это и выдавало генератор сильнее всего: у соседних отзывов совпадала жалоба слово в слово. `pickFresh()` запоминает последние `REPEAT_GUARD = 8` выдач каждого пула (ровно страница) и исключает их. Обычный «шафл-бэг» тут не годился: на стыке циклов последняя фраза одного круга и первая следующего вставали рядом.
  - Тексты генерируются **в порядке показа** — сначала персона, оценка и дата, потом сортировка по дате и только затем текст. Иначе защита считала бы соседями отзывы, которые на витрине стоят в разных местах: `reviewDate()` добавляет разброс, и порядок по индексу не совпадает с порядком по дате.
  - Пулы держим не меньше девяти строк, иначе окно запрета урезается до размера пула. Редко используемые пулы (подарки, контекст возраста) короче — их выдачи и так расходятся на десятки отзывов.
- **В пулах лежит только мужская форма фразы** — род расставит `alignPhrase()`. Пара «Получил…» и «Получила…» двумя записями не даёт разнообразия: после выравнивания это одна и та же строка, зато пул кажется вдвое больше, и повторы всплывают вдвое чаще.
- **В `GENDER_FORMS` нельзя класть глагол, у которого подлежащее — не автор.** «попал» превратил бы «Курьер не попал в интервал» в «Курьер не попала», «разобрался» испортил бы «Ребенок быстро разобрался». Каждую новую пару сверяй по пулам. Проверять удобно эвристикой: у женских персон искать слова на `-л`, у мужских — на `-ла`, и глазами отсеять курьера, коробку и ценник.
- **Числа отзывов у товаров не повторяются** (`REVIEW_COUNTS`): одинаковые счётчики у соседних карточек — первое, что выдаёт сгенерированный набор.

Подарок супругу или партнёру подбирается по полу автора (`giftFor()`): «покупала жене» на витрине читается как ошибка.

## Фото товара вписывается в кадр

Загруженное фото приводится к квадрату `1200×1200` на фоне `#f5f5f7`: `-trim` убирает однотонные поля, товар вписывается в 92 % кадра (`CONTENT_RATIO`).

**Обрезка идёт двумя проходами, а допуск подбирается** (`TRIM_FUZZ = [2, 8, 15]`). Строгие 2 % годятся для ровной заливки, но у части снимков фон — мягкий градиент, и на нём строгая обрезка не находит ничего: кадр остаётся целиком, товар ужимается вместе с пустыми полями. `contentBox()` идёт от строгого допуска к мягкому и берёт первый, при котором рамка стала заметно меньше кадра (`TRIM_MIN_GAIN`); тем же допуском потом режет и `squareTransformArgs()`. Начинать со строгого важно, чтобы не съесть белый товар. Снимок товара обычно на белом, а наш кадр докрашивается серым `#f5f5f7` — разница больше 2 % fuzz, поэтому один `-trim` снимал только серую рамку и останавливался на белом прямоугольнике исходника. В логе это выглядело как «товар 975×726» у фото, где товар на самом деле мелкий. Второй проход убирает белое поле.

Размер товара **считается заранее** — `contentBox()` прогоняет обе обрезки и отдаёт результат в `info:`, файл при этом не меняется. По этому размеру выбирается `-resize`:

- товар крупнее поля — уменьшаем (как раньше);
- товар мельче — **увеличиваем**, но не больше чем в `MAX_UPSCALE` (8×). Кадры, снятые «в полразмера», без этого выглядели мельче остальных. Потолок был 3.5×, и его пришлось поднять: исходники с товаром высотой ~140 px упирались в него и оставались на 41 % кадра рядом с соседями на 92 % — на витрине это выглядело как брак обработки, хотя обработка отрабатывала верно. На студийных рендерах Apple (ровные матовые поверхности почти без фактуры) 8× даёт лёгкую мягкость на гранях, но не мыло; для снимка с мелким текстом такой запас был бы велик.

Без этого работал только флаг `-resize 1056x1056>`, который умеет лишь уменьшать: снятый мелко товар оставался крошкой в центре карточки (файл 1200×1200 весом 4 КБ — почти весь фон).

Что видит ImageMagick на конкретном снимке — покажет `node photo-doctor.js [id-товара]`. Старые фото приводит в порядок `node refit-photos.js --apply` (перезаписывает файлы под теми же именами, ссылки в каталоге не трогает).

### Крупные планы деталей уходят в конец галереи

Часть фотографий с buy-страниц Apple — не снимок товара, а крупный план детали: угол корпуса, блок камер, экран с интерфейсом. Обработка тут ни при чём (замер на боевых данных: поля 4 % проставлены верно у всех 529 файлов), но в ленте между обычными ракурсами такой кадр читается как «фото обрезали». Место им — после общих видов, как у Apple.

`node sort-photos.js` показывает такие кадры с адресами, `--apply` уводит их в конец списка фото товара. Перестановка **стабильная**, поэтому внутри каждой цветовой группы и вариации ремешка они тоже становятся последними — галерея фильтрует список по варианту, а относительный порядок сохраняется. Скрипт идемпотентен: повторный прогон даёт «к перестановке 0».

- **Геометрии для распознавания мало.** Первая версия считала срезанным всё, что заполняет кадр, — и записала туда Mac mini сверху: он квадратный, но целый. Решают **углы рамки содержимого**: у целого товара силуэт со скруглениями, поэтому в углах фон (замер 0.85–0.97), у срезанного объект доходит до угла (0.41–0.56).
- **Уровня два, и это не перестраховка.** Строгий (упирается в кадр **обеими** сторонами + занят угол) переставляет сам — 25 кадров из 529. Широкий (упирается длинной стороной) ловит ещё и вертикальные крупные планы, но вместе с ними **целые снимки тёмных прямоугольных товаров**: у MacBook Air на тёмных обоях экран доходит до углов рамки, хотя ноутбук в кадре весь. Отличить их по готовому файлу нечем — исходник с полями до обработки не сохраняется. Поэтому широкий уровень только печатает список (69 кадров), а порядок владелец меняет сам перетаскиванием в форме товара.
- Витрины это не касается: вся работа офлайн, в рендере не прибавилось ни одного действия. Углы меряются только у снимков, которые вообще упираются в кадр.

## Отметка карточки не лежит на фото

«Хит», «Новинка», «Нет в наличии» — это **строка над названием, а не плашка в углу снимка**. Угловая плашка была обречена: товар вписан в 92 % кадра (см. выше), свободного поля в углу почти нет, и подпись ложилась прямо на телефон или ноутбук. На мобильном хуже вдвое — карточка там в половину ширины экрана, а плашка того же размера.

Как устроено сейчас (`productCard` в `lib/render.js`):

- отметка занимает **слот категории** — тот же кегль, вес и трекинг, отличается только цветом (`.card-flag` в `styles.css`). Поэтому строка над названием у всех карточек одной высоты и ритм сетки не меняется, а `.card-media` не содержит ничего, кроме снимка;
- цвет — `#bf4800`, тот же оранжевый, каким Apple подписывает «Новинка» на светлом фоне. Не `var(--accent)`: акцент у сайтов свой, и светло-зелёный `#34c759` в 11 px на белом не читается;
- **процент скидки уехал к цене** — `−13%` стоит рядом с зачёркнутой ценой, ровно как на странице товара. Старая цена и процент обёрнуты в `.price-was`, чтобы на узкой карточке они переносились на вторую строку вместе, а не порознь;
- поэтому «Хит» и скидка больше не вытесняют друг друга: раньше показывалась только одна плашка из трёх. У распроданного процент всё же прячется — «−13%» на том, что нельзя купить, обещание впустую;
- **распроданное видно по снимку** — `.card-out` гасит фото (`opacity` + `grayscale`). Подпись сверху и кнопка снизу легко проскакивают мимо взгляда, а фото читается первым;
- на экранах уже 420 px трекинг строки чуть плотнее (`@media(max-width:420px)`): без этого «Выбор покупателей» разрывалось на две строки.

## Блок доверия и плотность рядов выбора

Под кнопкой покупки — три довода: «**100%** оригинал», «**1 год** гарантия», «**Оптовая** цена» (`TRUST_ITEMS` и `TRUST_BLOCK` в `lib/render.js`). Жирным идёт то, что отличает предложение, обычным — что это такое.

- **Плашек нет намеренно.** Раньше это были три серых прямоугольника: они спорили с синей кнопкой и съедали первый экран. Теперь волосяная линия сверху и тонкие разделители между колонками, как в таблицах характеристик Apple. Высота блока упала с ~60 до 36 px.
- **Глифы берутся из `BENEFIT_GLYPHS`** — того же набора, что и бегущая строка главной: холст 35×35 и волосяная обводка, поэтому вес штриха на всей витрине один. Добавлен `verified` (кружок с галочкой) для «оригинала»: щит занят гарантией, а два щита подряд читались бы как одно обещание дважды. Спрайт сюда не тянем — на странице товара каждый глиф встречается ровно раз, а `<use>` окупается только повтором.
- На узкой колонке (≤1100 px) блок становится столбиком, и **разделители обязаны стать горизонтальными**: вертикальные повисли бы слева от текста чёрточками ни к чему.

Ряды выбора (цвет, конфигурация, доп. характеристики, ремешки) сжаты: у Mac групп бывает пять сразу, и на прежних отступах кнопка покупки уезжала за первый экран — покупатель не видел цену и кнопку одновременно.

- **Сжатие действует только на десктопе.** Высота кнопки варианта там 40 px, а в `@media(max-width:800px)` возвращается 44 px и кружок цвета 36 px: пальцем по 40 px попадают плохо.
- Правила ремешков (`.band-tab`, `.variant-sub`, `.band-colors`) лежат в CSS **ниже** блока `/* Страница товара */`, поэтому переопределить их оттуда нельзя — при равной специфичности побеждает последнее правило. Их значения правятся на месте.

## Слоган на телефоне — одна строка

Слоган стоит в двух местах — в заголовке первого экрана (после яблока) и в подвале, — и на телефоне переносился на вторую строку, оставляя там пару слов. Обе строки, а заодно и ряд правовых ссылок в подвале, теперь помещаются в одну: кегль подбирается под ширину экрана.

Подбирает его CSS: `font-size:min(23px, calc((100vw - поля)/var(--fit)))` плюс `white-space:nowrap`. **Длину строки в em (`--fit`) считает сервер** — `heroFit()` и `footFit()` в `lib/render.js`, значение уходит в атрибут `style` заголовка и `.foot-note`. Скриптом в браузере это мерить нельзя: страница сначала покажет крупный заголовок и дёрнется, а числом в CSS не задать — слоган пишет владелец.

- **Ширины символов — таблица `FIT_WIDTHS`**, десять групп по замеру системного шрифта. Точность нужна односторонняя: заниженная оценка выносит строку за экран, завышенная лишь делает кегль на пару процентов меньше нужного. Поэтому спорные символы округлены вверх, а незнакомый считается широким.
- **Запас зависит от кегля** (`FIT_DENSE`). Одна и та же строка на мелком кегле занимает больше em, чем на крупном: у системного шрифта свой трекинг на каждый размер и отдельное начертание для мелкого — от 23 px к 10 px набегает 11 %. На этом первая версия и погорела: длинный слоган вылезал за экран именно там, где кегль падал ниже 12 px. Кегль прикидывается по длине строки на типичном телефоне (`FIT_REF = 349` — сколько ему остаётся под текст).
- Учитывается и то, чем строка набрана: яблоко (`FIT_MARK`, те же `.6em + .26em`, что у `.apple-mark`), полужирное начертание заголовка (`FIT_BOLD`) и брендовый шрифт сайта (`FIT_FONTS` — засечковые шире системного). Подвал набран обычным системным шрифтом, поэтому у него своя оценка.
- Длинный слоган из-за всего этого ужимается сильнее — это цена одной строки. Проверено на посевных слоганах: на ширинах 320–800 px ни один не вылезает, худший занимает 97 % строки.
- У `var(--fit,21)` есть запасное число: подстановка `var()` без значения делает весь `font-size` недействительным, и кегль унаследовался бы от родителя.
- **Правовые ссылки считать не нужно** — подписи свои, не владельца, поэтому их длина (31,3em на две) вписана в CSS числом `32.9`. Менять подписи, не пересчитав константу, нельзя — это закреплено тестом. Уже 340 px ссылки возвращаются в столбик: кегль мельче 9 px читать невозможно.

## Зачёркнутая цена следует за вариантом

Основную цену на странице товара пересчитывает `applyVariant()` в `public/app.js`, а старая цена и процент раньше оставались серверными — от базовой сборки. У iPhone 15 Pro на 1 ТБ выходило «93 990 ₽» рядом с «64 990 ₽» и «−12%»: получалось, что более дорогая сборка ещё и выгоднее.

Теперь пересчитываются все трое. Доплата за память, ремешок и доп. характеристики одинакова в обеих ценах, поэтому **зачёркнутая = база сравнения + та же доплата**: выгода в рублях сохраняется, а процент от суммы честно уменьшается (у 15 Pro −12% на базе → −8% на 1 ТБ).

- База сравнения приходит в `data-base-compare` на кнопке «в корзину» — рядом с `data-base-price`. **Ноль означает «зачёркивать нечего»**: у товара без `oldPrice` и без активной акции самих элементов в разметке нет, и скрипт к ним не обращается.
- Старая цена и процент помечены `id="product-old-price"` и `id="product-save"`. Разметка и `app.js` держатся вместе тестом — правило уже ломалось молча, потому что при выборе варианта ошибку видно только глазами.
- Процент прячется через `style.display`, а не атрибут `hidden`: у `.save` свой `display`, и `[hidden]` из браузерной таблицы его не перебьёт.
- Карточки каталога это не затрагивает — там вариант не выбирают.

### Как эта пара выглядит

- **Старая цена на странице товара — 21px, а не 15px.** Под сплошной чертой мелкий текст не читался: сумму было видно, а разобрать нельзя. Вместе с кеглем чинится и сама черта — `text-decoration-thickness:1px` и `text-decoration-color` светлее цифр, поэтому линия проходит по сумме, а не закрашивает её. Тонкая линия задана и базовому `.old-price`, то есть в карточках каталога тоже.
- **Процент выгоды — залитая плашка `#0b7a37` с белым текстом** (контраст 5.4:1, проходит AA даже на 11px в карточке). Прежний светло-зелёный текст на светло-зелёном фоне рядом с крупной ценой пропадал. Цифры набраны `tabular-nums`, чтобы ширина плашки не прыгала при смене варианта.

## Стрелки галереи стоят на кромке кадра

Товар вписан в 92 % квадрата (см. «Фото товара вписывается в кадр»), значит свободного поля по бокам всего 4 % — на кадре шириной 570px это 23px. Стрелка 42px, отступавшая от края на 16px, заходила внутрь на 58px и ложилась прямо на телефон.

- **От 1200px кнопка садится на границу кадра, половина снаружи** (`left:-21px`): внутрь она заходит ровно на пустую кромку и снимок больше не закрывает. Порог именно 1200, а не 900: у`же места слева уже нет — на 1100px вынесенная стрелка упиралась в самый край окна (замер: 3px до кромки экрана).
- **Ниже порога стрелка внутри, прижата к краю** — 6px на планшете, 4px на телефоне против прежних 12–16px.
- Вынос и размер связаны числом: `-21px` это ровно половина от 42px. Меняешь размер — пересчитывай отступ, это закреплено тестом.
- Появился `:focus-visible` — до этого кнопку нельзя было увидеть с клавиатуры.

## Ремешки часов

У часов есть поле `bands` — коллекции ремешков: `[{name, sizes:[{label}], options:[{name, hex, add, inStock}]}]`. `add` — доплата к цене часов, как у памяти; наличие задаётся по вариации.

В форме владельца коллекции хранятся строками в скрытом `<textarea name="bands">`:

```
# Trail Loop | S/M, M/L
- Синий/чёрный | #2b4a7d | 0
- Оранжевый/бежевый | #c8622a | 0 | нет
```

`#` — коллекция и её размеры, `-` — цветовая вариация (`цвет | hex | доплата | нет`). Разбирает `parseBands()` в `server.js`, интерфейс рисует `public/band-editor.js` — в нём вводится **полная цена** часов с ремешком, доплата считается сама.

На витрине (`lib/render.js`) разметка всех коллекций выводится сразу, а переключение вкладки только показывает нужную — поэтому выбор мгновенный. Итоговая цена = база + память + ремешок + размер ремешка. Позиция корзины — `id + память + цвет + ремешок + размер ремешка` (`itemKey` в `public/app.js`), поэтому одни часы с разными ремешками это разные строки.

**Смена коллекции сбрасывает размер, а не оставляет прежний.** `showGroup()` зовёт `pickSize(null)`, когда у новой коллекции размеров нет, и `pickSize` обязана этот случай отработать — раньше она выходила по `if (!btn) return`, и «M/L» от Trail Loop уезжал в корзину вместе с ремешком, у которого такого размера не бывает. Сервер такую позицию не принимает (`variantMissing` проверяет размер так же строго, как сам ремешок), поэтому покупатель видел «нет в наличии» на том, что есть. В текущем каталоге размеры есть у всех коллекций, так что поймать это можно было только добавив коллекцию без размеров.

### Две привязки у снимка, а не одна

Один и тот же ремешок на натуральном и на чёрном титане выглядит по-разному, поэтому у фото **две независимые привязки**: `imageColors[файл]` — цвет корпуса, `imageBands[файл]` — вариация `Коллекция|Цвет`. Они не исключают друг друга: «Alpine Loop · Terra Cotta на чёрном титане» несёт обе.

- В форме товара у миниатюры **два селекта**: `imgcolor:<файл>` и `imgband:<файл>` (`productForm` в `lib/owner-views.js`, `photo-manager.js` для только что загруженных). Один общий селект со значением `band:…` терял корпус при каждом сохранении формы — снимок становился общим и показывался под всеми корпусами сразу.
- Маршрут `/owner/products/:id/images/color` меняет только то поле, которое пришло (`color` или `band`); второе остаётся прежним.
- Фото грузятся **сразу в пару**: `band-editor.js` рисует поле загрузки под каждой вариацией, а переключатель корпуса над плитками задаёт, к какому корпусу пойдут снимки; `/owner/products/:id/images/add` принимает `color` и `band` одновременно. Счётчики у плиток обновляются после загрузки/удаления через хук `window.bandUploadsRefresh`.
- Группы снимков в панели — пары «ремешок + корпус»; фото с ремешком не дублируется в группе корпуса.

Галерея показывает **один набор — самый точный из непустых**, а не склейку всех (`applyFilter()` в `app.js`): ремешок+корпус → ремешок без корпуса → корпус без ремешка → общие. Склейка и была тем самым «всё в кучу»: рядом с фото чёрного корпуса шли снимки натурального. Тот же порядок повторяют `productPage` (стартовый кадр, чтобы страница не открывалась с чужого варианта) и `/api/cart` (фото позиции корзины).

Вариации «в цвет корпуса» (`forColor`) сервер прячет сразу в разметке, а не только скриптом; в `band-editor.js` эта привязка пишется в строку хвостом `| @Корпус` — без этого она стиралась при каждом сохранении формы.

Наборы ремешков с ценами РФ лежат в `catalog.js` (`BANDS`). Перенести их в живой каталог на сервере: `node sync-bands.js --apply`.

## Раскладка оформления: шаги слева, деньги справа

Оформление собрано из **трёх контейнеров**, а не из «список слева, форма справа»: `#checkout-items`, `#checkout-form` и правая панель `.checkout-rail` с `#checkout-side` внутри. Товары и форма идут одной колонкой сверху вниз тремя нумерованными шагами («Ваш заказ» → «Получатель» → «Доставка»), а справа липнет только сводка по деньгам.

Прежняя раскладка отдавала форме узкую полосу 390 px, пока широкая колонка с одним товаром стояла почти пустой: покупатель заполнял пять полей в вертикальной кишке рядом с пустым местом. Теперь форма получает всю ширину — имя с фамилией встают в две колонки, СДЭК и OZON рядом, а не столбиком.

- **Раскладка — именованные области grid** (`grid-template-areas:"items rail" "form rail"`), и это не украшательство: на телефоне порядок обязан быть **товары → сумма → форма**, а из вложенной обёртки сводку между ними не поставить. В медиазапросе области переставляются в `"items" "rail" "form"`. Сумма внизу, после кнопки, никому не видна, а знать её надо до заполнения.
- **Форма собирается один раз** (`form.dataset.ready`) — иначе смена количества стирала бы введённое. Сводка, наоборот, перерисовывается целиком: она короткая, и возиться с отдельными id ради трёх строк смысла нет.
- **Число товаров в сводке — `availableCount()`, а не `count()`.** Сумма считается без распроданных позиций, и рядом с ней должно стоять то же число: с общим `count` строка читалась как «три товара за 67 990», хотя в цену вошёл один. Заголовок блока «Ваш заказ» при этом считает все строки — он описывает список, а не деньги.
- Позиции внутри блока — **строки с волосяной линией, а не карточки**: своя рамка у каждого товара внутри карточки шага давала рамку в рамке.
- **Ширина правой панели — `clamp(300px,26vw,360px)`.** Фиксированные 360 px на экране 1024 px забирали у формы почти половину, и ряды выбора вставали в две тесные колонки.
- **Доводы в панели — `TRUST_BLOCK_COL`**, тот же список, что на странице товара, но в колонку: три в ряд в 300–360 px не встают, а медиазапрос по ширине **окна** про ширину этой панели ничего не знает.
- **Кнопка не на всю ширину колонки** (`.co-submit` — 440 px по центру): растянутая на 870 px синяя полоса выглядит тяжелее, чем читается, а правовая подпись под ней рвалась посреди слова.
- Номер шага — тонкий кружок с приглушённой цифрой, а не залитая плашка: акцент у сайтов свой, и светлый заливкой под белой цифрой не читается (та же причина, что у отметок карточки и плашек оплаты в панелях).
- При пустой корзине форма, панель и подзаголовок скрыты (`.is-empty`), остаётся одна карточка по центру.

## Получатель и доставка на оформлении

Заказ идёт с предоплатой и уезжает перевозчиком, поэтому расплывчатых «уточним при подтверждении» на оформлении не осталось: **обязательны имя, фамилия, контакт, способ доставки и адрес**. Проверяет и витрина (сразу, без ожидания ответа), и `/api/order` заново — клиентским данным не верим, как и в цене заказа.

- **Имя и фамилия хранятся раздельно** (`firstName`, `lastName`), но `customerName` остаётся собранной строкой: по ней рисуются обе панели и уведомления в Telegram, и у прежних заявок она единственная. Иначе весь список заказов пришлось бы переписывать ради одного поля.
- **Способы доставки — `lib/delivery.js`**, закрытый список (`СДЭК`, `OZON`). Один на всех: по нему рисуется выбор, проверяется заказ и подписывается строка в панелях. Отдельный модуль, а не константа в `render.js`, потому что список нужен и в `lib/db.js` при нормализации, а `db.js` рендер подключать не может — вышел бы цикл (`render → tenancy → db`).
  - **`id` попадает в заказ и остаётся в старых заявках навсегда** — менять их нельзя, только добавлять новые. Название правится свободно.
  - Витрина берёт список **от сервера**, атрибутом `data-delivery` на `#checkout-page`, а не держит свой: разъехавшийся список означал бы выбор, который сервер потом не принимает. Закреплено тестом.
  - **Логотипы перевозчиков — `lib/delivery-logos.js` и `public/delivery/<id>.svg`** (подробности формата — в `public/delivery/README.md`). Только SVG, инлайном спрайтом в страницу: чётко на любом экране, ни одного лишнего запроса, 800 байт на два логотипа в уже сжатом HTML. PNG пришлось бы отдавать в 2× и 3× и он всё равно мылится на промежуточных масштабах, а внешние адреса запрещены CSP (`img-src 'self' data:`) — и посетителя незачем показывать чужому серверу.
    - **Файла нет — остаётся название текстом**, и высота строки та же (`.co-choice-mark` с `min-height`), поэтому карточки с логотипом и без не разъезжаются. Это и есть состояние по умолчанию.
    - Высота фиксирована (19 px), ширина — по пропорции из `viewBox`: вордмарки у перевозчиков разной длины, и подгонять их под общую ширину значило бы искажать. **Без `viewBox` файл игнорируется** — по нему масштабируется `<use>`.
    - **Файлы приходят снаружи, поэтому чистятся до вставки**: `<script>`, `<foreignObject>`, обработчики `on*` и ссылки на внешние адреса. Инлайн чужого SVG в HTML исполняет всё, что внутри.
    - **Служебные id внутри логотипа получают приставку** (`dl-cdek-a`). В брендбуках это сплошь `id="a"`, и без приставки второй логотип на странице красился бы градиентом первого — та же грабля, что была у плейсхолдеров товаров с «десятками одинаковых id».
    - Логотипы читаются **один раз при старте**, как глифы характеристик, поэтому после добавления файла нужен `pm2 restart istore`.
  - Чужое значение сводится к пустому, как и отсутствие поля у прежних заказов, поэтому `nameOf()` отдаёт пустую строку, а не «undefined».
- **Первый способ выбран заранее.** Пустой выбор заставлял бы покупателя ткнуть лишний раз, а строка «Доставка» в итогах висела бы без значения.
- **`initDeliveryChoice()` синхронизирует итоги сразу, а не только на `change`.** При сборке разметки радио в DOM ещё нет, поэтому `deliveryName()` возвращал «выберите способ» при уже выбранном первом способе — на этом я и наступил.
- Подсказка под адресом зависит от перевозчика («адрес пункта выдачи СДЭК» / «постамата OZON»), поэтому названия в скрипте встречаются — но это подсказка, а не список: тест запрещает именно дубль списка (`id: 'cdek'`), а не упоминание имён.
- **Стоимость доставки не считается**: в итогах стоит название перевозчика, сумма заказа — только товары. Тарифы СДЭК и OZON зависят от региона и веса, а считать их нечем — внешних зависимостей у проекта нет. Если понадобится, естественный шаг — фиксированная цена на перевозчика в панели владельца.
- Разметку строки заказа в панелях (доставка, адрес, комментарий старых заявок) даёт общая `R.orderDelivery()`, а не копия в каждой панели: подписи там уже расходились.

## Онлайн-оплата (CrocoPAY)

Приём платежей через [CrocoPAY](https://crocopay.tech/developer?type=express), схема **Express**: одним POST создаём платёжную ссылку и уводим покупателя на форму CrocoPAY. Реквизиты карт через наш сервер не проходят вовсе — поэтому Express, а не H2H (там пришлось бы показывать номер чужой карты у себя и опрашивать статус счёта в цикле).

Ключи кассы задаются в `/owner/settings` → «Онлайн-оплата (CrocoPAY)»: Client ID, Client Secret и базовая валюта. Берутся в кабинете CrocoPAY: «Кассы» → шестерня. Настройки **общие на все домены**, как ключ dadata.ru, и **на витрину не попадают** — браузер знает только `data-pay="1"` на `#checkout-page`.

**По умолчанию оплата выключена.** `enabled()` требует и галочку, и оба ключа: галочка без ключей давала бы кнопку, которая всегда ошибается. Пока выключено, витрина работает как прежде — заявка, менеджер связывается; ни одного запроса к платёжке не уходит.

### Как это снять, если платёжка отвалится

1. Снять галочку в `/owner/settings` — этого достаточно, витрина сразу возвращается к прежнему поведению.
2. Если убирать код: удалить `lib/crocopay.js`, блок между `/* ====== ОПЛАТА: CrocoPAY` и `/* ====== /ОПЛАТА: CrocoPAY` в `server.js`, `require` этого модуля там же и в `lib/owner-views.js`, секцию настроек в `settingsPage`, `paymentPage` в `lib/render.js`, `paymentBadge` и её вызовы в обеих панелях, `startOrderPayment`/`settleOrderPayment` в `lib/db.js`, функции способа оплаты в `public/app.js`.
3. **Данные заказов при этом целы.** Оплата живёт необязательным полем `payment`, миграции не нужны ни туда, ни обратно.

### Почему оплата не подменяет статус заказа

Состояние платежа — отдельное поле `payment`, а НЕ новое значение `status`. Статусы («новый / в работе / выполнен / отменён») ведёт менеджер, и подмешивать туда оплату значит терять одно из двух: заказ бывает одновременно и оплачен, и в работе. Поля нет — «оплата не запускалась», поэтому все прежние заказы читаются без изменений.

Состояния: `pending` — ссылка выдана, ждём вебхук; `paid` — подтверждено; `mismatch` — вебхук с верной подписью, но сумма меньше ожидаемой, и заказ должен посмотреть человек. Из `mismatch` в `paid` дорасти можно, обратно — нет.

### Порядок шагов: заказ первым, оплата поверх

`/api/order` создаёт и записывает заявку как раньше, и только потом витрина зовёт `/api/pay/crocopay/start`. Поэтому упавшая платёжка **не теряет заказ**: покупатель видит номер и кнопку «Повторить оплату», менеджер получает заявку в Telegram как обычно. Обратный порядок («сначала оплата») стоил бы заявки при любой ошибке платёжки.

- `/api/order` отдаёт `id` заказа и кладёт его в **подписанную cookie-сессию** покупателя (`req.session.myOrders`, последние 20) — тем же приёмом, что и id своего отзыва. Поэтому запустить оплату можно только по своей заявке, а не по чужой, угадав идентификатор.
- **Выбора «оплатить позже» на витрине нет** — оплата идёт сразу. Прежний путь «заявка, менеджер свяжется» остаётся ровно в одном случае: оплата вообще не настроена (нет галочки или ключей). Иначе кнопка вела бы в платёжку, которой нет. Отсюда `submitLabel()`: «Перейти к оплате» либо «Оформить заказ».
- Адрес формы приходит из ответа платёжки, и мы отправляем по нему покупателя, поэтому `safeRedirect()` пропускает **только https и только `crocopay.tech`**. Иначе подменённый или ошибочный ответ увёл бы покупателя куда угодно.

### Вебхук: подписи мало, нужен ещё token

**В теле вебхука нет идентификатора заказа вовсе** — только `timestamp`, суммы и `sign`. Какой это заказ, говорят GET-параметры `callbackUrl` (платёжка их сохраняет). Отсюда два независимых условия:

- **подпись** (HMAC-SHA256 по `timestamp|subtotal|percentage|charge_percentage|charge_fixed|total` с Client Secret) подтверждает, что вебхук от CrocoPAY;
- **`token`** — одноразовые 16 случайных байт, записанные в `payment.token` при старте оплаты — подтверждает, что он про **этот** заказ. Без него одного перехваченного вебхука хватило бы на любую заявку с той же суммой, потому что подпись сумму покрывает, а заказ — нет.

Не сошлось что-то одно — **403 и ничего не меняем**, как в документации. Сверка идёт до записи, это закреплено тестом.

- **Подпись считается по ТЕКСТУ значений, а `JSON.parse` его теряет.** В документации `charge_fixed` показан и как `0`, и как `"0.00000000"`, а `0.50` после разбора и обратной сборки станет `0.5` — HMAC не сойдётся. Поэтому `lib/server-lib.js` сохраняет тело JSON ещё и как есть (`req.rawBody`, не больше 64 КБ — мегабайты загрузок в памяти ради подписи держать незачем), а `signMessages()` строит до двух строк-кандидатов: из разобранного тела и из сырого. Обе проверяются тем же секретом, так что подобрать подпись это не помогает; зато вебхук проходит и когда платёжка присылает form-data (в примере проверки у них `$_POST`, а не JSON).
- **Суммы в разных единицах.** В запрос `amount` идёт в основных единицах (`67990.00`), а в вебхуке `subtotal`/`total` — в минимальных (`6799000`). На этой асимметрии легко ошибиться в сто раз, поэтому ожидаемую сумму пишем сразу в минимальных (`toMinor()`).
- **Меньше ожидаемого — не «оплачено»** (`mismatch` + запись расхождения). Больше или равно — считаем оплаченным: при мульти-гео плательщик выбирает свою страну, сумма пересчитывается по курсу и приходит **в его валюте**, то есть численно почти всегда больше рублёвой. Строгое равенство ломало бы каждый такой платёж.
- **Идемпотентность обязательна**: платёжка вправе повторить вызов. `settleOrderPayment` возвращает `changed`, и Telegram уходит только на реальное изменение. Уже оплаченный заказ повторным «Оплатить» не сбрасывается — иначе новый `token` отверг бы вебхук по прежней ссылке.
- Вебхук приходит **только на успех**, поэтому «не заплатил» здесь не обрабатывается: заказ остаётся в `pending` и его разбирает менеджер.

### Возврат покупателя — не подтверждение оплаты

`/pay/success` и `/pay/cancel` — обычные страницы витрины. Успех подписан «Мы проверяем платёж», а не «Оплачено»: подтверждает оплату только вебхук, а на эти адреса покупатель попадает и просто закрыв форму. Обещать «оплачено» раньше вебхука — значит однажды пообещать это тому, кто не заплатил. У отмены кружок нейтрально-серый (`.order-success-neutral`): зелёный читался бы как успех.

**В `trackPage` эти страницы намеренно не попадают** — иначе их пришлось бы вносить и в `metricPublicPath()`, а живой посетитель уехал бы в «неподтверждённые автоматические запросы» (см. «Подводные камни»).

Тариф у сервиса — P2P-процессинг **от 14 % для RUB** (Visa/MC/MIR и СБП), ставка пересчитывается ежемесячно от оборота. Это заметно больше обычного эквайринга, и на маржу серого импорта влияет прямо — учитывай при выставлении цен.

## Подводные камни

- **Процесс слушает только петлю (`HOST`, по умолчанию `127.0.0.1`).** Открытый наружу порт 3000 сводил на нет защиту входов: при `TRUST_PROXY=1` приложение верит `X-Forwarded-For`, поэтому любой, кто ходил на порт напрямую в обход Caddy, подставлял новый «IP» на каждую попытку пароля и обходил счётчик попыток (проверено: 6 попыток с одного заголовка → 429, с ротацией — ни одной блокировки). Через `X-Forwarded-Host` там же выбирался любой магазин по имени. `HOST=0.0.0.0` оставлен на случай прокси на другой машине — тогда порт обязан быть закрыт файрволом.
- **Пустой блок в CSS-сетке всё равно занимает ячейку.** У магазина без Telegram и телефона `.footer-contacts` рендерился пустым и добавлял в подвал лишний зазор на ровном месте, поэтому блок выводится только когда контакт реально задан. На телефоне подвал центрируется целиком (`@media(max-width:800px)`): в две колонки там не встать, а колонка по левому краю читается как сбитая вёрстка. Десктопная раскладка в две колонки не менялась.
- **`\b` в регулярках не работает с кириллицей** — в JS это граница ASCII-слова, поэтому `\bгб\b`, `\bсон\b`, `\bчас` не срабатывают никогда. Русские слова пиши без `\b`.
- Порядок правил в `RULES` важен: «шумоподавление» содержит «давление», поэтому audio идёт раньше hypertension; «до 26 ч видео» — battery раньше video; «Apple Pencil (USB-C)» — pencil раньше port; «спутниковые сообщения, Emergency SOS» — satellite раньше sos.
- Ключ важнее значения там, где значение сбивает: «Порты: 2× USB-C, MagSafe 3» — это порты, а не зарядка; «Память: 256 ГБ» — накопитель, а не размеры.
- `storages` — универсальное поле вариантов: у часов там размеры корпуса, у остальных память. Подпись выбирает `variantLabel()` в `render.js`.
- Позиция корзины определяется как `id + память + цвет` (`itemKey` в `public/app.js`) — один товар в разных вариантах это разные строки.
- Цена заказа **всегда пересчитывается на сервере** (`/api/order` в `server.js`), клиентским данным не верим.
- `db.readJson` возвращает закэшированный объект по ссылке — не мутируй его без последующего `write*`.
- Номера заказов — `max + 1` от уже выданных, не длина списка.
- Ссылка и кнопка «в корзину» в карточке — соседи, а не вложены (`<article class="card">` → `<a class="card-link">` + `<div class="card-add">`).
- **«В корзину» кладёт товар и сразу уводит на `/checkout`** — тем же путём, что и повторный клик по товару, который уже в корзине. Раньше первый клик только менял подпись кнопки и счётчик в шапке, и до корзины надо было нажимать второй раз. `Cart.add()` поэтому **возвращает признак успеха**: на отказе (корзина переполнена, битая позиция) переход не делается — покупатель остаётся на месте и видит подсказку. Всплывающей подсказки на успехе больше нет, она гасла вместе со страницей. Закреплено тестом.
- **В карточке каталога кнопка «В корзину» — ссылка на страницу товара, а не добавление**, если у товара есть хоть один вариант (цвет, конфигурация, ремешок, доп. характеристика). Иначе вариант выбрали бы за покупателя. На текущем каталоге вариант есть у всех 43 карточек, поэтому кнопка-добавление в сетке не встречается ни разу — прямое добавление осталось на случай товара совсем без вариантов.
- Плейсхолдеры товаров — один спрайт `PH_SPRITE` на страницу (`lib/render.js`), карточки ссылаются на него через `<use href="#ph-…">`. Раньше каждая карточка несла копию SVG и свой `<linearGradient id="g">` — десятки одинаковых id на странице.
- Статика с меткой версии (`?v=`) отдаётся с `max-age=31536000, immutable` — при правке файла меняется хеш в `assetV()`, поэтому кэш не залипает.
- **Сравнение с `NaN` всегда ложно.** `if (rating < 1 || rating > 5)` пропускало отзыв без оценки, и тот молча становился пятизвёздочным. Числа из формы проверяй через `Number.isInteger` / `Number.isFinite`, а не диапазоном.
- `content: attr(X)` в `::after` читает атрибут **того элемента, к которому прикреплён псевдоэлемент**, а не родителя. Подпись корпуса на фото ремешка поэтому висит на `.img-chip-media[data-case]`.
- `k in body` истинно для `constructor`, `toString` и прочих ключей прототипа — поля формы разбираются через `hasOwnProperty` (`own()` в `server-lib.js`).
- Страницы, которые считает `trackPage`, обязаны быть и в `metricPublicPath()`. Иначе сервер пишет посещение как предварительное, клиент его не подтверждает, и живой посетитель через две минуты уезжает в «неподтверждённые автоматические запросы».
- `HEAD` обслуживается обработчиком `GET` (`routeMethod` в `server-lib.js`) — тело Node не отправит сам, а 404 на живой витрине ломал мониторинги.

## Проверка после правок

Тесты — встроенный `node --test`, без раннера и зависимостей:

```bash
npm test
```

`test/core.test.js` держит `App` и рендер в памяти (свой `request()`/`response()` вместо сети), поэтому проверки идут без запуска сервера и без записи в `data/`. Утверждения про вёрстку читают `public/styles.css` и `public/app.js` как текст — так закрепляются правила, которые уже ломались: закрытое `:root{…}` в админке, `attr(data-case)` на том же элементе, подпись варианта в корзине.

Плюс ручная проверка синтаксиса и чистого запуска:

```bash
node --check server.js && for f in lib/*.js public/*.js catalog.js seed-data.js; do node --check "$f" || echo "FAIL $f"; done
rm -rf data && PORT=3999 node server.js &   # чистый запуск на демо-данных
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3999/
```

Полезная проверка каталога — что каждой характеристике подобралось своё правило и нет промахов. Сверять надо через `hasIcon()`, а **не** по имени `sparkles`: этот глиф выбирается и намеренно (см. «Built for AI» выше), поэтому сравнение с именем даёт семь ложных срабатываний на Mac.

```bash
node -e '
const c=require("./catalog"), {hasIcon}=require("./lib/spec-icons");
let fb=0;
for (const p of c.products) for (const l of String(p.specs).split("\n")) {
  if (!l.trim()) continue;
  const i=l.indexOf(":"), k=i>-1?l.slice(0,i).trim():"", v=i>-1?l.slice(i+1).trim():l;
  if (!hasIcon(k,v)) { fb++; console.log("нет правила:", p.name, "|", l); }
}
console.log("товаров:", c.products.length, "| без правила:", fb);
'
```

## Адрес доставки и подсказки dadata.ru

На оформлении вместо «Комментария» — поле **«Адрес или пункт выдачи»** с подсказками. Оно **обязательное**: заказ идёт с предоплатой и уезжает перевозчиком (см. «Получатель и доставка на оформлении»). Заказ хранит его в `order.address`; поле `comment` осталось в `db.createOrder` только ради старых заявок — панели показывают его, если он есть (`R.orderDelivery()`, общая на обе панели).

Ключ «Подсказок» лежит в глобальных настройках (`dadataToken`, задаётся в `/owner/settings`) и **на витрину не попадает**: браузер спрашивает наш `/api/address-suggest`, а в DaData ходит уже сервер (`lib/dadata.js`, обычный `fetch`, таймаут 4 с). Класть клиентский ключ в HTML не стали — его тривиально увести со страницы.

Ответ маршрута — `{ok, configured, items}`. `configured: false` значит «ключа нет»: витрина после такого ответа больше не спрашивает до перезагрузки. Ошибка сети или таймаут — это `ok: false` при `configured: true`, и следующий ввод снова попробует. В обоих случаях поле остаётся обычным вводом, оформить заказ это не мешает.

Запросы в DaData платные по счётчику, поэтому витрина их бережёт: минимум 3 символа, пауза 220 мс после последней буквы, повтор той же строки не отправляется (`initAddressSuggest()` в `public/app.js`). На вводе адреса в 21 символ уходит один запрос. Сервер сверху ограничивает 90 запросами в минуту с IP.

Список — `role="listbox"` с клавиатурой (↑/↓/Enter/Esc); выбор ловится на `mousedown`, потому что `click` приходит уже после `blur`, когда список закрыт.

## Правила

- Никаких внешних зависимостей — только встроенные модули Node. `package.json` держим без `dependencies`.
- Всё пользовательское экранируем через `esc()` из `lib/render.js` перед вставкой в HTML.
- Цены в `catalog.js` — ориентир российского рынка, редактируются там же или в админке.
